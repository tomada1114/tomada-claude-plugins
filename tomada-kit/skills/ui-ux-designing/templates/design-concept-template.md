# デザインコンセプト テンプレート

`docs/design/design-concept.md` の雛形。この文書は「何をどう決めたか、なぜそう決めたか」を残す
ためのもので、実装可能な値は対になる `design-system-template.md` 側に置く。

## 使い方

- これは足場であって、埋めるべき穴の一覧ではない。会話で実際に決まった節だけを書き、決まって
  いない節は既定値で埋めずに節ごと削る。理由: 空欄や無難な既定値が残ると、読み手である実装
  セッションがそれを決定事項として扱ってしまう。
- 長さは中身に合わせる。決定が3件しかない節を3ページに水増ししない。逆に、議論が深かった節は
  この雛形の行数を超えてよい。
- 各項目には値だけでなく「なぜそれを選び、何を捨てたか」を1行添える。理由が書けない項目は、
  まだ決まっていない項目なので削って質問に戻す。
- 未決を残す場合は `未決: <何が決まれば決まるか>` と書く。空欄のまま残さない。
- 以降の `## 概要` からがコピー対象。見出しレベルはそのままで `docs/design/design-concept.md`
  に貼り、この「使い方」節は持ち込まない。

| 項目 | 内容 |

### テーマ方針

ライトとダークを対等に扱い、どちらでも同じ情報量・同じ階層が伝わることを前提にする。
理由: OS 側のテーマ設定が既定の入力であり、片方を「おまけ」にすると対比や階層がそこだけ崩れる。

- 実装方式: `:root` に `color-scheme: light dark` を置き、値は `light-dark()` で両モード分を1行に書く
- ユーザーによる明示切替: 要る / 要らない（要る場合は `[data-theme]` で `color-scheme` を上書きする）
- 既定で寄せる側があるならその理由: （無い場合はこの行を削る）

## デザイン原則

2〜4個。決まった数だけ書き、埋めるために足さない。原則は「迷ったときにどちらを取るか」を
決めるためにあるので、トレードオフの片側を名指しできない文は原則ではなく標語として削る。

### 1. [原則名]

[1〜2文の説明]

- この原則が効く判断: [具体的な分岐を1つ]
- この原則のために捨てるもの: [失われる価値]

### 2. [原則名]

[同上]

## ブランド軸

形容詞ペアで position を取り、UI 上の現れ方まで書く。理由: 「モダン」「クリーン」のような
単独の形容詞は誰も否定しないため、実装セッションに対して何の制約にもならない。

| 軸 | 位置（1–5） | UIでの現れ方 |
|------|------|------|
| 静か ⇔ にぎやか | | 色数、動きの量、同時に見せる要素数 |
| 硬質 ⇔ やわらかい | | 角丸、コントラスト、書体のふところ |
| 端正 ⇔ 手作り感 | | 整列の厳密さ、イラストの有無、余白の均一さ |
| 情報密度: 高 ⇔ 低 | | 1画面あたりの行数、余白、フォントサイズ |
| 実直 ⇔ 遊び心 | | コピーの語り口、マイクロインタラクション、空状態の見せ方 |

不採用にした軸の位置と理由: [例: 「にぎやか」側に振らなかったのは、長時間の連続利用で疲れるため]

## 主要フロー

プロダクトの中心となる3〜4本を画面列で書く。画面ごとの仕様より先にフローを置く。理由:
実装セッションが最初に必要とするのは画面の一覧ではなく、画面の間で何が持ち越されるかの情報。

### フロー1: [名前]

- ユーザーの目的: [その人が片付けたい用事]
- 起点: [どこから入ってくるか。通知 / 共有リンク / ホーム]
- 画面列: `[画面A] → [画面B] → [画面C] → [完了]`
- 各遷移のきっかけ: [A→B は何を押したときか、B→C は何が満たされたときか]
- 持ち越す情報: [画面をまたいで保持する状態]
- 完了の合図: [何をもってユーザーは終わったと分かるか]
- 分岐: 失敗したとき / 対象が0件のとき / 未ログインのとき に、どこへ行くか

### フロー2: [名前]

[同じ形式]

### フロー3: [名前]

[同じ形式]

## 画面別UI仕様

上のフローに登場した画面だけを書く。フローに出てこない画面は、まだ必要性が確認できていない
画面なので足さない。コンポーネント名は `design-system.md` のインベントリの名前で呼ぶ。

### [画面名]

- 登場フロー: [フロー1, フロー3]
- この画面の役割: [1文。ユーザーがここで下す判断]
- 領域構成（上から）:
  1. [領域名] — [載せるもの]
  2. [領域名] — [載せるもの]
  3. [領域名] — [載せるもの]
- 主アクション: [1つだけ。画面内で最も目立つもの]
- 副アクション: [複数可。主アクションより弱く見せる]
- 使用コンポーネント: [Button(primary), Card(elevated), ...]
- 状態: 初期 / 読み込み中 / 空 / エラー / 権限なし で何を出すか
- 画面幅による変化: [段組が変わる幅と、そこで何が畳まれるか]
- この画面で意図的に置かないもの: [理由付きで]

## ボイス&トーン

UIコピーは実装セッションが最も自由に発明してしまう領域なので、語り口と用語を先に固定する。

### 基本方針

| 項目 | 決定 |
|------|------|
| 人称 | 「あなた」 / 主語を省く / その他 |
| 文体 | です・ます / だ・である |
| 文の長さ | [例: ボタンは6文字以内、説明文は1文40字以内] |
| 感嘆符・絵文字 | 使う場面を限定するか、使わないか |

### 用語集

同じ概念を2つの言葉で呼ばない。理由: 「保存」と「登録」が混在すると、ユーザーは別の操作だと
解釈する。

| 使う語 | 使わない語 | 対象 |
|--------|-----------|------|
| | | |

### 場面別の書き方

| 場面 | こう書く | こうは書かない | 理由 |
|------|---------|---------------|------|
| エラー | 「接続できませんでした。通信環境を確認して再試行してください」 | 「エラーが発生しました」 | 原因と次の行動が無いと、ユーザーは同じ操作を繰り返すしかない |
| 空状態 | 「まだ[X]がありません。最初の[X]を作成しましょう」 | 「データがありません」 | 空は失敗ではなく開始地点なので、次の一手を置く |
| 破壊的操作 | 「3件を完全に削除します。取り消せません」 | 「本当によろしいですか？」 | 対象数と可逆性が判断材料なので、それを文に入れる |

## アイコノグラフィと画像方針

### アイコン

- セット: [Lucide / Phosphor / Material Symbols / SF Symbols から1つ]。1セットに固定する。
  理由: 線の太さと角の処理がセットごとに違い、混在すると同一画面内で品質差として見える
- 線の太さ / サイズ: [1.5px] / 16・20・24px の3段
- 色は `currentColor` で継承させ、アイコン自体に色を持たせない
- アイコンだけのボタンにはラベルを付ける（読み上げ用のラベルと、ポインタ環境でのツールチップ）
- 意味を色だけに載せない。形でも区別できるアイコンを選ぶ

### 画像・イラスト

- 方針: [写真中心 / イラスト中心 / 抽象グラフィック / 画像を使わない]
- 選んだ理由と、選ばなかった方針を捨てた理由:
- イラストを使う場合のスタイルと出所: [線画 / フラット / 3D、1つの出所に統一する]
- 生成画像の可否と使ってよい範囲:
- 標準のアスペクト比: [16:9 / 4:3 / 1:1]。領域は `aspect-ratio` で先に確保する
- 意味のある画像には代替テキストを付け、装飾画像は `alt=""` で読み飛ばさせる

## 決定ログ

この表になる。理由: 決定そのものより「何を却下したか」が失われやすく、それが失われると
同じ議論が繰り返される。
