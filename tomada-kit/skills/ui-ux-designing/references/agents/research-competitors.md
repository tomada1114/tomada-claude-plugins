# 競合UX調査（サブエージェント用プロンプト）

サブエージェントを起動できないホストでは、本体セッションがこのプロンプトをそのまま自分で実行する（読み込み・調査・出力形式は同じ）。

モデルは `sonnet` を1体だけ使う。理由: 対象アプリ・評価軸・出力形式がすべて確定済みで、判断ではなく仕様確定の定型的な情報収集にあたる。
<!-- derived from orchestrating-models §2 -->

| プレースホルダ | 埋めるもの |
|---|---|
| `{{SKILL_DIR}}` | このスキルの絶対パス |
| `{{PRODUCT_SUMMARY}}` | Phase 1 で確定したプロダクト概要（2〜3行） |
| `{{TARGET_USER}}` | 対象ユーザー像（状況・動機・制約） |
| `{{APP_TYPE}}` | アプリタイプ（`app-type-ux-patterns.md` / `-verticals.md` の節名） |
| `{{APPS}}` | 本体側で確定した調査対象アプリ3つ以上（サブエージェントに選ばせない） |
| `{{FLOWS}}` | 比較する主要フロー3〜4本（「初回登録→最初の成果」を必ず含む） |
| `{{OUTPUT_PATH}}` | 調査サマリーを書き出す絶対パス |

---

{{APP_TYPE}} のプロダクトについて、競合3つ以上のUXを調査してください。

意図: この調査結果は、次フェーズでユーザーに提示するデザイン方向性の選択肢を組み立てる材料であり、そのままユーザーにも共有されます。裏の取れていない主張が1つ混ざると、その上に積む選択肢ごと誤ります。断定するなら出典を付け、確認できなかったことは「未確認」と書いてください。

前提（Phase 1 で確定済み。ここは調べ直さない）:
- プロダクト概要: {{PRODUCT_SUMMARY}}
- 対象ユーザー: {{TARGET_USER}}
- アプリタイプ: {{APP_TYPE}}
- 調査対象アプリ: {{APPS}}
- 比較するフロー: {{FLOWS}}

最初に {{SKILL_DIR}}/references/research-methods.md を全文読んでください。3段構成の手順、検索クエリの形、記事の採否条件、出力の節名がそこにあります。以下はその要約なので、細部は必ず原典に従ってください。

手順:
1. Jobs to Be Done を3〜5個、「[状況]のとき、[動機]したいので、[期待する結果]を得たい」の形で書く。競合を見る前に書き、以降の評価はすべて「そのJobが片付くか」で判定する。
2. {{FLOWS}} の各フローを、全競合について同じ順で辿る。比較単位は画面ではなくステップ数と各ステップの内容。実機で辿れないものは記事から再構成し、その旨を明記する。
3. research-methods.md の6観点ルーブリックで各競合を1〜5点で採点する。観点は増やさない。点数には1行の理由を添える。

調査の制約:
- 検索は web検索で行い、クエリ内の年は実行時の西暦に置き換える。
- ヒットした記事は公開日を確認し、2年以上前の「トレンド」記事は根拠に採用しない（原則・ガイドラインの一次情報は対象外）。
- 主張ごとに出典URLを持つこと。出典の無い断定は書かない。実機で確認したものは「実機確認」と書く。
- 自分でサブエージェントを起動しないこと。この調査は1セッションで完結させる。

出力: {{SKILL_DIR}}/references/research-methods.md の「調査結果のユーザーへの共有」にある調査サマリー形式で、次の節を**この名前・この順序で**すべて埋める。

```
## 調査サマリー
### 対象と前提
### Jobs to Be Done
### フロー比較
### ヒューリスティック評価
### 避けるべきパターン
### 自プロダクトへの示唆
### 参照ソース
```

書き出し先: {{OUTPUT_PATH}}

最終メッセージは調査サマリー本文だけにしてください。検索結果の原文、途中の作業ログ、読んだ記事の要約は返さないこと。判断が割れて決めきれなかった論点は、「自プロダクトへの示唆」の「判断が割れる点」に選択肢の形で残してください（そこで決めない）。
