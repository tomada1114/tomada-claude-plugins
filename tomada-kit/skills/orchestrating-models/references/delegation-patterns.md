## 委譲指示の書き方

サブエージェントはこの会話のコンテキストを持たずコールドスタートする。曖昧な指示は聞き返しか手戻りになり、節約分が消える。委譲プロンプトには必ず以下を含める:

1. **ゴール**: 何ができたら完了か(検証可能な形で)
2. **意図**: なぜこれが必要か、成果物が何を可能にするか。意図を渡すと、指示していない関連情報に自力で接続できる
3. **スコープ**: 触ってよいファイル/ディレクトリ、触ってはいけない範囲。適用範囲は「全件に」と言い切る
4. **前提知識**: この会話で判明した事実・決定事項を要約して渡す(再調査させない)
5. **出力契約**: 返してほしい形式(変更ファイル一覧、findings リスト、判断が必要になった点)
6. **エスカレーション条件**: 判断に迷ったら独断せず「未解決」として報告させる

Sonnet に渡す場合、1〜3 に穴があると失敗する。穴が埋まらないなら、そのタスクは Opus に渡すか、先に仕様確定の一段を挟む。

## リレー編成

1 タスクを 1 モデルに丸投げしない。段ごとに得意なモデルを当てる。サブエージェントの数が増えてもトータルでは安く速い。

「判断」段の担当はメインモデル自身(Fable でも Opus でも)。メインが Opus のときは、実装段も自分で持つほうが速い場面が多い(姿勢差は `references/delegation-triage.md`)。

### 調査リレー(広く集めて、統合する)

| 段 | 担当 | 内容 |
|---|---|---|
| 収集 | Sonnet / Haiku × N 並列 | 領域を分割して事実だけ集めさせる。解釈させない |
| 統合 | Opus × 1 | 各報告を突き合わせ、矛盾・欠落・重複を整理して構造化する |
| 判断 | メイン | 整理済みの成果に対して方針を決める |

メインが生の調査結果を全部読むのは高い。**統合作業自体を委譲する**のがこのリレーの肝。ただしメインが Opus で、読んだ内容そのものを後の設計に使うなら自分で読む。

### 実装リレー(仕様を確定してから流す)

| 段 | 担当 | 内容 |
|---|---|---|
| 仕様確定 | メイン | 設計判断、受け入れ条件、スコープ境界を書き下す |
| 実装 | Opus | 複数ファイル・リファクタ・e2e。完全な仕様を渡して走らせる |
| 仕上げ | Sonnet | テスト追加、CI を通す、コミット、PR 作成 |

仕様が最初から明確で、既存パターンの反復にすぎないなら、実装段も Sonnet でよい。**「Opus か Sonnet か」の分岐点は仕様の確定度**。

### レビューリレー(検出とフィルタを分ける)

| 段 | 担当 | 内容 |
|---|---|---|
| 検出 | Opus / Sonnet × N | 観点ごとに分けて**全件報告**させる。confidence と severity を付けさせる |
| 検証・選別 | Opus | 各 finding を反証的に検証し、誤検知を落としてランク付けする |
| 採否 | メイン | 直すもの・別チケットにするものを決める |

検出段に「重大なものだけ」「保守的に」と書かない。忠実に絞られて recall が落ちる。選別は必ず別段に置く。

## 実行手段の使い分け

| 状況 | 手段 |
|---|---|
| 自己完結する実装・調査の 1 単位 | サブエージェント(Agent ツール、`model` 指定) |
| 大規模・分解可能・検証重視(監査、広範リサーチ、横断変更) | Dynamic Workflow(`agent()` で `model` + `effort` を段ごとに指定) |
| 完了条件を定義して無人で回せる実装 | /goal + `authoring-goal-prompts` スキルで goal プロンプトを作成し別セッションへ |
| 会話的な質問・単一の小さな編集 | 委譲しない(オーバーヘッド負け) |

`CLAUDE_CODE_SUBAGENT_MODEL` で既定モデルを固定する運用もあるが、全サブエージェント(レビュー系スキル内部のものも含む)に効くため、呼び出しごとの指定を優先する。

## 並列化と非同期化

- 独立な調査・検証は 1 レスポンスで複数サブエージェントを同時起動する。直列に待つのは依存関係があるときだけ
- サブエージェントの完了をブロックして待たない。走らせたまま次の段の設計(メインが Opus なら自分の担当作業)を進め、脱線や文脈不足を検知したときだけ介入する
- 長く続く作業は毎回新規起動せず、`SendMessage` で同じサブエージェントを継続させる。コンテキストが維持されキャッシュも効く
- Dynamic Workflow ではフェーズ内並列・フェーズ間直列を守る。全件が揃わないと次に進めない場合だけバリアを置く

## スキルのプリロード

繰り返し説明している規約・チェックリストはスキル化し、委譲プロンプトで「~/.claude/skills/<name>/references/... を読んでから作業せよ」と指定する。毎回のインライン説明分のトークンが消える。

ただしスキルを **過度に規範的にしない**。細かく手順を縛りすぎたスキルは、上位モデルの既定の振る舞いより質を下げる。既定で十分にできることは書かない。

逆に、実行のたびに結論が同じになる静的な決定(ワークフロースキルの段ごとのモデル割当など)はプリロードの対象にしない。結論をそのスキルへベタ書きする(SKILL.md §2 の「焼き込み」)。プリロードが見合うのは、実行時の状況で結論が変わる判断・チェックリストだけ。

## 結果の受け取り

- 結果は要約(結論・変更点・未解決事項)で受け取り、生ログや全文 diff をメインのコンテキストに戻させない
- 検証が必要な成果物は「検証もサブエージェント側で実施し、実行したコマンドと結果を報告」させる。メインは報告の整合性だけを見る
- ただし **Opus の委譲先に「検証ステップを入れよ」とは書かない**。過剰検証になる。求めるのは「何を実行し、どういう結果だったかの報告」であって、追加の検証手順の指示ではない
- 長時間ランでは、実装したサブエージェント自身ではなく **fresh context の verifier サブエージェント**に仕様との突き合わせをさせる
