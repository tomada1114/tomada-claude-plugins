## 委譲指示の書き方

サブエージェントはこの会話のコンテキストを持たずコールドスタートする。曖昧な指示は聞き返しか手戻りになり、節約分が消える。委譲プロンプトには必ず以下を含める:

1. **ゴール**: 何ができたら完了か(検証可能な形で)
2. **意図**: なぜこれが必要か、成果物が何を可能にするか。意図を渡すと、指示していない関連情報に自力で接続できる
3. **スコープ**: 触ってよいファイル/ディレクトリ、触ってはいけない範囲。適用範囲は「全件に」と言い切る
4. **前提知識**: この会話で判明した事実・決定事項を要約して渡す(再調査させない)
5. **出力契約**: 返してほしい形式(変更ファイル一覧、findings リスト、判断が必要になった点)
6. **エスカレーション条件**: 判断に迷ったら独断せず「未解決」として報告させる

7. **完了の証拠と本数の上限**: 完了条件は「どこで何が通ったか」(PR の CI が緑、など)で書き、ローカルで回すゲートの手順は書かない。サブエージェント自身がさらに起動してよい本数も書く

ブリーフに「`just verify` を通してから PR」のようなゲート手順を書くと、過剰検証になるうえ、並列の本数ぶんフルゲートが同じマシンで同時に走る。ビルド・テストスイートが重いリポジトリを複数本並列に委譲するときは、「ローカルは編集で壊しうる狭いチェックだけ、全体は CI に任せる」と前提知識として渡す(hook の迂回は別問題で、常に禁止のまま)。

`executor` に渡す場合、1〜3 に穴があると失敗する。穴が埋まらないなら、先にメインで仕様を確定させるか、メインが自分で実装する。

`architect`(Fable 5.2 high)に渡す場合、禁止や承認の条件は書かれたとおりに守られる。禁止は対象の操作を名指しして理由と例外を同じ文に入れ、確認なしで進めてよい操作も書く。コードを書き換えさせるなら所有の扱い(構造ごと任せるか、頼んだ箇所だけか)を書く。文言は `model-playbooks.md` の「architect に渡すとき」。

## リレー編成

1 タスクを 1 つの段に丸投げしない。段ごとに `scout`・`executor`・`architect` を当て分ける。`architect` は 1 本が高いので、各リレーで 1 本を基本にする。

「判断」段の担当はメイン自身。実装段も自分で持つほうが速い場面が多い(委譲する理由は `references/delegation-triage.md`)。

### 調査リレー(広く集めて、統合する)

| 段 | 担当 | 内容 |
|---|---|---|
| 収集 | `scout` × N 並列 | 領域を分割して事実だけ集めさせる。解釈させない。1 本が読む量は 100k トークン未満に収める |
| 統合 | メイン(量が多く、中身を後で使わないなら `architect` × 1) | 各報告を突き合わせ、矛盾・欠落・重複を整理して構造化する |
| 判断 | メイン | 整理済みの成果に対して方針を決める |

scout の報告は結論だけなので、数本ならメインが直接読んで統合する。報告が多く、読んだ内容そのものを後の設計に使わないときに限って、統合を `architect` に委譲する。

### 実装リレー(仕様を確定してから流す)

| 段 | 担当 | 内容 |
|---|---|---|
| 仕様確定 | メイン | 設計判断、受け入れ条件、スコープ境界を書き下す |
| 実装 | メイン / `executor` / `architect` | 設計判断が残るならメイン、確定仕様でまとまった量なら executor(完全な仕様を渡して走らせる)、ブリーフに書き出せる難所だけ architect |
| 仕上げ | `executor` | テスト追加、CI を通す、コミット、PR 作成 |

**実装段の分岐点は仕様の確定度と難しさ**(`delegation-triage.md` の分水嶺)。

### レビューリレー(検出とフィルタを分ける)

| 段 | 担当 | 内容 |
|---|---|---|
| 検出 | `architect` × 1〜2(Workflow で観点ごとに多数並列にするなら `'opus'` + `'high'`) | 観点ごとに**全件報告**させる。confidence と severity を付けさせる |
| 検証・選別 | `architect`(件数が少なければメイン) | 各 finding を反証的に検証し、誤検知を落としてランク付けする |
| 採否 | メイン | 直すもの・別チケットにするものを決める |

検出段に「重大なものだけ」「保守的に」と書かない。忠実に絞られて recall が落ちる。選別は必ず別段に置く。

## 実行手段の使い分け

| 状況 | 手段 |
|---|---|
| 自己完結する実装・調査の 1 単位 | サブエージェント(Agent ツール、`subagent_type: executor` / `architect` / `scout`) |
| 大規模・分解可能・検証重視(監査、広範リサーチ、横断変更) | Dynamic Workflow(`agent()` で `model` + `effort` を段ごとに指定。下の「Workflow の段の割当」) |
| 完了条件を定義して無人で回せる実装 | /goal + `authoring-goal-prompts` スキルで goal プロンプトを作成し別セッションへ |
| 会話的な質問・単一の小さな編集 | 委譲しない(オーバーヘッド負け) |

### Workflow の段の割当

`agent()` は段ごとに `model` と `effort` を取る。名前付きエージェントと同じ割当を、段の仕事の形で当てる。Workflow は並列の本数が多く、段の単価がそのまま本数倍で効くので、Haiku 5.5 に流せる段を見落とさない。

| 段の仕事 | `model` + `effort` | 例 |
|---|---|---|
| ファイルを書き換えない、判断を含まない収集・列挙・要約(ツールを使う) | `'haiku'` + `'xhigh'`(= `scout`) | discover(対象ファイル・呼び出し箇所の洗い出し)、Understand の並列リーダー、Research の広域スイープ、ログやテスト結果の要約 |
| プロンプトに渡した材料だけで答える判定・書き出し(ツールを使わず、`schema` で返す) | `'sonnet'` + `'high'`(= `worker`) | 渡した finding を基準どおりに分類・ラベル付け、重複判定、決まった形式への書き出し |
| 仕様が確定した書き換え | `'opus'` + `'low'`(= `executor`) | Migrate の各サイトの変換、一括修正 |
| 多数並列に回す検出・観点別レビュー | `'opus'` + `'high'`(Workflow だけの段) | Review の観点別の検出段、judge panel の各審査員 |
| 選別・反証・最終の統合など、結論を決める判断 | `'fable'` + `'high'`(= `architect`) | adversarial verify、検出結果の選別とランク付け、最終の統合 |

- `'opus'` + `'high'`($3.46/task)は Workflow だけの段。観点別の検出のように同じ形の判断を多数並列に回すとき、全本を `'fable'` + `'high'`($9.08)にすると本数倍で効くので、検出は Opus 5.5 high に広く当て、結論を決める段だけ Fable 5.2 high にする。本数が 2〜3 本なら全部 `'fable'` + `'high'` でよい
- 検証役(refute・judge)が自分でコードを読んで真偽を決めるなら、それはエージェント作業の判断なので Opus 5.5 high 以上。Haiku の判定段は、判断材料をすべてプロンプトに入れられるときに限る
- Haiku の段は 1 本のプロンプトを 100k トークン未満に収める。超えるとそのリクエスト全体の単価が 5 倍になる。読む範囲は件数で割って本数を増やす
- `schema` 付きの Haiku 段はそのまま使える。公式ガイドが挙げる「思考オフ + JSON 形式でツール呼び出しを飛ばす」問題は、思考が常にオンの Claude Code では起きない
- `'haiku'` が Haiku 5.5 を指すのは Anthropic API の場合だけ(Claude Code v2.1.293 以上)。Bedrock・Google Cloud・Foundry では Haiku 4.5 になり、effort が効かない
- Haiku の段の出力は後段(統合・verify の段、またはメイン)で受け止める。Haiku だけで完結させて結論にしない

`agent()` で `model` と `effort` を省くとメインの Fable 5.2 medium を引き継ぎ、本数ぶん高くつく。必ず添える。

`CLAUDE_CODE_SUBAGENT_MODEL` で既定モデルを固定する運用もあるが、全サブエージェント(レビュー系スキル内部のものも含む)に効き、effort は固定できないため、`subagent_type` での指定を優先する。

## 並列化と非同期化

- 独立な調査・検証は 1 レスポンスで複数サブエージェントを同時起動する。直列に待つのは依存関係があるときだけ
- サブエージェントの完了をブロックして待たない。走らせたまま自分の担当作業を進め、脱線や文脈不足を検知したときだけ介入する
- 長く続く作業は毎回新規起動せず、`SendMessage` で同じサブエージェントを継続させる。コンテキストが維持されキャッシュも効く。ただし追加する仕事の段が違うときは継続しない。`architect` に原因調査を任せたあとの「ブランチを追従させて CI 緑でマージ」のような機械的な後始末は、文脈が要らなければ `executor` に新規で渡す。`SendMessage` で続行させるときは「続けて」ではなく、何をやるかを書く
- 複数リポジトリへ同じ変更を横展開するときは、1 本で正となる変更を作ってから残りを並列に流す。最初から全本並列にすると壁時計時間は縮むが、本ごとに書きぶりが割れ、揃え直しの手間が残る(手順の詳細は `rolling-out-harness-changes`)
- `scout` の調査は、対象が 1 リポジトリでも全文を読ませると 100k トークンを超えやすい(数百行の文書 1 本とその参照元すべてを洗うと 30 万トークン前後になった実例がある)。読むファイルと問いを絞り、超えそうなら問いごとに本数を分ける
- Dynamic Workflow ではフェーズ内並列・フェーズ間直列を守る。全件が揃わないと次に進めない場合だけバリアを置く

## スキルのプリロード

繰り返し説明している規約・チェックリストはスキル化し、委譲プロンプトで「~/.claude/skills/<name>/references/... を読んでから作業せよ」と指定する。毎回のインライン説明分のトークンが消える。

ただしスキルを **過度に規範的にしない**。細かく手順を縛りすぎたスキルは、上位モデルの既定の振る舞いより質を下げる。既定で十分にできることは書かない。Fable 5.2 は書かれた注意書きを忠実に守るので、理由のなくなった「〜するな」や「サブエージェントを使え」という常設の指示は消す。

逆に、実行のたびに結論が同じになる静的な決定(ワークフロースキルの段ごとのモデル割当など)はプリロードの対象にしない。結論をそのスキルへベタ書きする(SKILL.md §2 の「焼き込み」)。プリロードが見合うのは、実行時の状況で結論が変わる判断・チェックリストだけ。

## 結果の受け取り

- 結果は要約(結論・変更点・未解決事項)で受け取り、生ログや全文 diff をメインのコンテキストに戻させない
- 検証が必要な成果物は、実行したコマンドと結果を報告させる。追加の検証手順は指示しない(過剰検証になる)。メインは報告の整合性だけを見る
- ユーザーへ伝える前に、報告の中の外部状態(PR がマージ済みか、コミット ID、CI の結論)を 1 回の読み取りで確かめる(`gh pr view <n> --json state,mergeCommit` など)。報告をそのまま転記しない
- 長時間ランでは、実装したサブエージェント自身ではなく **fresh context の verifier サブエージェント**に仕様との突き合わせをさせる
