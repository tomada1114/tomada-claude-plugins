# 未知(unknowns)発見テクニック

Thariq Shihipar(Anthropic / Claude Code チーム)の Field Guide がベース。前提となる考え方:

- **Map**: プロンプト・スキル・CLAUDE.md・会話で与えたコンテキスト
- **Territory**: 実際のコードベースと現実の制約

Map と Territory のギャップ(未知)が手戻りの原因になる。安価な事前ステップで未知を潰すほど、高コストな実装フェーズのやり直しが減る。未知は 4 象限で捉える:

| | 知っている | 知らない |
|---|---|---|
| **自覚あり** | Known Knowns | Known Unknowns(自覚あるギャップ) |
| **自覚なし** | Unknown Knowns(見て初めて言語化できる好み等) | Unknown Unknowns(考慮外) |

## 実装前

### Blind Spot Pass(Unknown Unknowns の発見)

不慣れなコードベース・新領域で最初にやる。調査自体はサブエージェントに委譲してよい。ただし「何が抜けているか」を見つける作業は曖昧さが大きいので **Opus** に渡す(Sonnet は与えられた観点の範囲しか見ない)。事実の列挙・ファイル収集だけを切り出すなら Sonnet/Haiku でよい。

> この codebase の認証まわりに新しいプロバイダを追加したいが、認証モジュールの構造を何も知らない。私が考慮できていないはずの unknown unknowns(既存の規約、暗黙の依存、過去の設計判断)を洗い出す blind spot pass をして。

### Interview(Known Unknowns の解消)

計画前に、曖昧な点を Claude 側から質問させる。アーキテクチャに影響するものを優先し、些末な確認は後回し。

### Brainstorm & Prototype(Unknown Knowns の発見)

ビジュアルや UX など「見ないと良し悪しを言えない」領域は、先に HTML プロトタイプ等を安く作って反応を得る。言語化できない好みを実装前に言語化する。

### 実装計画の並べ方

変更しやすい・後から影響が大きい部分(データモデル、UX フロー)を計画の先頭に置き、そこへのフィードバックを最初に集める。

## 実装中

### implementation-notes.md

計画からの逸脱・エッジケースをログさせる。逸脱時は保守的な選択を優先させる。

> implementation-notes.md を維持して。計画にないエッジケースや逸脱が必要になったら、"Deviations" セクションに理由と選択肢を記録し、保守的な方を選んで進めて。

委譲先のサブエージェント/goal 実行にもこの運用を指示すると、メイン側は後から逸脱だけをレビューできる。

## 実装後

- **Explainer**: 変更内容・逸脱・未解決事項をまとめた共有用ドキュメントを作らせる(レビューコスト削減)。
- **Quiz**: 自分が変更を説明できるかクイズさせてからマージする(理解の未知を検出)。
