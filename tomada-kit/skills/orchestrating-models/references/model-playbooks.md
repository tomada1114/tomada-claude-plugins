## 共通(どの段に渡すときも)

- **意図を渡す**: 「何をやるか」だけでなく「なぜ必要か・成果物が何を可能にするか」を書く。意図が分かると、指示されていない関連情報に自力で接続できる。
- **適用範囲を言い切る**: 「全セクションに適用(最初の 1 つだけではない)」のように、一般化してほしい範囲を明示する。
- **出力形式と制約を先に**: 順序や網羅性が重要なら番号付きリストにする。
- **成果は根拠付きで報告させる**: 「報告する各主張について、このセッションで実行したツール結果を根拠として示せ。未検証なら未検証と書け」。
- **一時ファイルは片付けさせる**: 反復用のスクリプトやスクラッチを作ったら最後に消させる。

## Opus 5.5 の癖

- **仕様は最初に全部渡す**: 完全なタスク仕様を渡して走らせるのが最も強い。小出しに指示すると弱くなる。スタブや placeholder を残さず完遂する。
- **検証を指示しない**: 「最後に検証ステップを入れよ」「サブエージェントで確認せよ」「ダブルチェックせよ」は **過剰検証を招くので書かない**。放っておいても自己検証と自己修正をする。
- **スコープを固定する**: 頼まれていない手順を足しがち。「頼まれた範囲を、頼まれた粒度で。より良い方法があるなら一言添えたうえで依頼どおり進める。勝手に狭めたり広げたり作り変えたりしない」。
- **サブエージェント生成に上限を置く**: 自分でもサブエージェントを産みやすい。「サブエージェントは大きく独立した並列作業にのみ使う。数回のツール呼び出しで終わる作業は自分でやる。自分の成果の検証にサブエージェントを使わない。数は最小限」。
- **出力の長さを較正する**: 生成ドキュメントは長くなりがち。「文書の長さはタスクに見合わせる。要約の重複・定型セクション・水増しをしない」。
- **レビューでは絞らせない**: 「重大なものだけ」「保守的に」と書くと本当に報告数が減る。**網羅を求め、フィルタは別パスに分ける**(`delegation-patterns.md` のレビューリレー参照)。
- **思考ではなく根拠を求める**: 「思考過程を書き出せ / 説明せよ」ではなく、file:line、コマンド出力、成果物そのものを求める。
- **途中の報告で止まる**: 長い多段タスクでは、ツール呼び出しのない進捗報告でターンを終えることがある。無人ランでは完了条件をチェックリストで持たせ、未完の項目が残っていれば続行させる。詳細は `authoring-goal-prompts`。
- **1M コンテキストを活かす**: 長い文脈でも指示追従とツール呼び出しが安定する。

## executor に渡すとき

low は思考量が少ない。**仕様の穴を自分で埋めない**前提で渡す。

- 触るファイル・パス・出力形式を明示し、未解決の問いを残さない。穴が埋まらないなら、そのタスクは architect に渡すか、先にメインで仕様を確定させる
- 適用範囲は「全件に」と言い切る
- 設計判断に当たる箇所が出てきたら独断せず「未解決」として返すよう書く(定義本文にも入っている)
- 多段の推論が要ると分かっている作業は渡さない

## architect に渡すとき

high は思考量が多く、スコープを広げやすい。**ゴールと制約**を渡し、手順は縛りすぎない。

- 何が決着済みで何が未決かを分けて書く。決着済みの判断を蒸し返させない
- 設計判断をしたら、選んだ案と理由を報告に残させる
- レビュー・検出は全件報告 + confidence / severity。選別はメインか別段でやる
- 機械的な部分を切り出せるなら、architect ではなく executor に渡す

## effort とコスト

Artificial Analysis Intelligence Index v4.3.2 × Cost per Task(2026-09-22 取得)でパレート最適な組み合わせ:

| 組み合わせ | Index | Cost/Task | 限界コスト | この構成での役 |
|---|---|---|---|---|
| Sonnet 5 low | 24 | $0.51 | — | 使わない(Opus 5.5 low と $0.04 差で Index 24 対 42) |
| Opus 5.5 low | 42 | $0.55 | $0.002/pt | `executor` |
| Opus 5.5 medium | 51 | $1.34 | $0.088/pt | メインセッション |
| Opus 5.5 high | 54 | $1.82 | $0.160/pt | `architect` |
| Opus 5.5 xhigh | 56 | $3.46 | $0.820/pt | 既定にしない(品質差を実測した作業だけ、メインの `/effort` で) |
| Opus 5.5 max | 58 | $5.98 | $1.260/pt | 同上 |

Fable 5.1 と Opus 5 はどの effort でも劣位で、同じか安いコストでより賢い Opus 5.5 の段がある(Fable high 51 / $3.91 は Opus 5.5 medium 51 / $1.34 と同 Index、Opus 5 max 51 / $5.86 も同じ)。Fable の利用枠は Max プランの同一リミットの内数で、別枠ではない。

Opus 5.5 の effort 名は Opus 5 と比べられない。Opus 5.5 medium ≈ Opus 5 high で、low もいくつかのコーディング評価でそれに迫る。

**指定先:**

| 手段 | 段の指定 |
|---|---|
| メインセッション | settings.json の `model: claude-opus-5-5` と `modelSettings.claude-opus-5-5.effortLevel: medium`。一時的に上げるなら `/effort` |
| Agent ツール | `subagent_type: executor` / `architect`。定義 frontmatter の `model` と `effort`(`low` / `medium` / `high` / `xhigh` / `max` か整数)が効く。`model` だけの起動は modelSettings の medium で走る |
| Workflow の `agent()` | `model: 'opus'` と `effort: 'low'` / `'high'` を段ごとに指定する |

数値は API 価格ベースの Cost per Task で、Max プランでは消費量の目安として使う。出典ノート: `~/ghq/github.com/tomada1114/iobsidian/Content/_material/claude-model-effort-cost-performance.md`。
