## なぜエージェント作業は Opus 5.5 が軸で、scout と worker だけ Haiku 5.5 なのか

Opus 5.5 の medium / high / xhigh / max はパレート最適で、Fable 5.1・Opus 5・Sonnet 5 はどの effort でも、同じか安いコストでより賢い Opus 5.5 の段がある。Sonnet 5.5 は high(46.8 / $0.88)だけがパレート最適で、ほかの段は Haiku 5.5 max か Opus 5.5 の段に劣位。high も、executor の仕事には上積みが要らず、architect の仕事には Opus 5.5 high のほうが賢いので、間に挟む段にならない。だから**ファイルを書き換えるエージェント作業では**モデルを替えて段を作る理由がなく、Opus 5.5 の effort だけで段を作る。詳細は [model-playbooks.md](model-playbooks.md#effort-とコスト)。

Opus 5.5 low(42.3 / $0.55)は、Haiku 5.5 の暫定コストの上では Haiku 5.5 max(43.4 / $0.21)に劣位になった。それでも `executor` を替えないのは、Haiku のコストが 100k トークン超の 5 倍単価を含まない暫定値で、Anthropic 自身が複雑なエージェント型コーディングには Sonnet / Opus を勧めているから(Terminal-Bench 4.0 は Haiku 5.5 39.2% 対 Sonnet 5.5 70.6%)。書き換える仕事は間違えたときの手戻りが大きい。

例外は Haiku 5.5 の 2 段。どちらも賢さの段ではなく、仕事の形で決まる段になる。

- `scout`(Haiku 5.5 high): ファイルを書き換えない、判断を含まない調べ物。Anthropic が挙げる Haiku の用途(狭い範囲のサブエージェント、要約、分類)そのもので、間違えても何も壊れず、メインが結論を突き合わせて受け止められる。トークン単価は Opus 5.5 の 1/40(100k 超でも 1/8)
- `worker`(Haiku 5.5 xhigh): 完全なブリーフに 1 回の返答で答えるツールなしの仕事(書き出し・基準による判定)。手数が 1 回でプロンプトも 100k を超えないので、トークン単価の差がそのまま効く。xhigh(41.2)は以前の `worker`(Sonnet 5.5 medium、40.8)と同じ Index 帯。品質は後段の検査(lint・独立したレビュー・人)で受け止める前提になる

メインを medium に置くのは、判断と実行の両方を担う段として、low からの +9pt を $0.088/pt で買え、high 以上に上げるより上積みが安いから。サブを low と high の 2 段に絞るのは、メインが medium である以上、medium のサブに渡すものはメインがやっても同じ品質・同じ単価で、委譲の固定費だけが余分にかかるから。委譲する価値があるのは、メインより**安く済む**段(low)か、メインより**賢い**段(high)だけ。

xhigh / max はメインでもサブでも既定にしない。high → xhigh は +2pt に +$1.64、xhigh → max は +2pt に +$2.52 で、high までの限界コスト($0.16/pt)の 5〜8 倍になる。品質の差を実測で確かめた作業にだけ、メインの `/effort` で上げる。

## 委譲しないもの

**数回のツール呼び出しで終わる作業。** 委譲のブリーフを書く時間のほうが長い。

**手順が直列で、並列化の余地がない作業。** サブエージェントは並列性を買うための道具であって、作業を消す道具ではない。直列なら往復分だけ遅くなる。

**後で成果の中身が必要になる作業。** 委譲すると戻ってくるのは要約であって、読んだファイルの中身ではない。次の判断でその中身を使うなら、自分で読む。

**自分の成果の検証。** Opus は指示しなくても自己検証と自己修正をする。検証用サブエージェントを足すと二重になり、トークンだけ増えて品質は上がらない。委譲プロンプトに「最後に検証ステップを入れよ」「ダブルチェックせよ」と書かない。

**仕様がまだ固まっていない作業。** ブリーフに書けないことは委譲できない。固める作業自体がメインの仕事。「何を作るべきか」自体が未確定なら、ユーザーと一緒に固める。

**コンテキストを節約するためだけの委譲。** Opus は 1M コンテキストを持ち、その全域で指示追従とツール呼び出しが安定する。「main のコンテキストが埋まるから」だけでは根拠として弱い。埋まる内容を**後で使わない**ときに限って根拠になる(下記 3)。

## 委譲する 4 つの理由

これ以外の理由で委譲しない。

**1. 独立並列トラック。** 互いに依存しない、それぞれ相応の大きさがある調査・実装が複数本あるとき。1 レスポンスで同時に起動し、各トラックを下の分水嶺で executor / architect に振る。判定: 「A の結果を見てから B を始める」なら並列ではない。順序が要るならフェーズを分ける。

**2. 機械的作業のコスト裁定 → executor。** 仕様が確定していて成否が明確な作業は、low が medium の半額以下($0.55 対 $1.34/task)で同じ結果を出す。テスト追加、カバレッジ引き上げ、CI を通す、コミット、PR 作成、一括置換、フォーマット、確定仕様どおりの実装。出力トークンは入力の数倍の単価なので、**まとまった量の書き出し**ほどこの裁定が効く。

**3. コンテキスト隔離 → scout。** 大量のファイルを読む必要があるが、**読んだ内容自体は後で使わない**とき。読んだ結果を受けてファイルを書き換えるなら executor。「40 ファイル読んで、この規約がどこで破られているかだけ知りたい」は委譲。「40 ファイル読んで、その構造を踏まえて設計する」は自分で読む。

**4. ブリーフに書き出せる難所 → architect。** medium では落ちる、または落ちそうな段(多段の推論が要る実装・検証、レビュー、散在情報の統合)を、会話の文脈なしで完結する形に切り出せるとき。high は medium から +3pt に +$0.48 で、Index 帯として最安の上積み。切り出せない難所は委譲せず、メインの `/effort` を一時的に high に上げる。

## executor と architect の分水嶺

分けるのは**仕様の確定度**で、作業の種類や大きさではない。同じ「実装」でも両方に振り分かれる。

| executor(low) | architect(high) |
|---|---|
| 仕様が確定していて、成否をコマンドで判定できる | 仕様に穴があり、埋めること自体が設計判断になる |
| 既存パターンの反復(同じ形のハンドラ・テスト・設定を増やす) | 最初の 1 本がパターンになる(骨組み、インターフェース、スキーマ、エラー体系) |
| 1 か所の変更で完結する、または変更箇所が機械的に列挙できる | 複数ファイル・複数層にまたがり、変更間の整合を取る必要がある |
| 判断を含まない整形(調査・収集・列挙だけなら scout) | 散在した情報を突き合わせて矛盾・欠落を整理する統合 |
| 決定済みの内容の削除・移行 | コードレビュー、バグ発見、原因究明 |
| 2 回までの単純な CI 修正 | 同じ失敗が 2 回の修正を生き延びた CI 修復 |

迷ったら「委譲先が聞き返してきそうか」で決める。聞き返されそうなら architect。executor に投げて仕様不足で聞き返されたら、それは一段上に投げるべきだった合図で、同じ段に詳しいブリーフを足すより architect に上げるほうが早い。

逆方向の失敗もある。仕様が確定している作業を architect に渡すと、high の思考量で頼まれていない設計判断をやり直したり、スコープを広げたりする。確定仕様の実装は executor に渡し、ブリーフに「設計は決着済み」と書く。

委譲プロンプトに足す一文(完全な仕様を先に渡す、生成上限、スコープ固定)は `model-playbooks.md` の「Opus 5.5 の癖」にある。

## scout と executor の分水嶺

分けるのは**ファイルを書き換えるかどうか**。

| scout(Haiku 5.5 high) | executor(Opus 5.5 low) |
|---|---|
| 読んで答えるだけ(コード検索、条件に合う箇所の全件列挙、規約違反の洗い出し) | 読んだ結果を受けて直す(一括置換、違反箇所の修正) |
| Web で事実を集め、出典付きで返す | 集めた事実をドキュメントに書き込む |
| テストやビルドの結果を読んで要約する | テストを足す、CI を通す、コミット・PR を作る |

どちらも「判断を含まない」が前提で、解釈が要るなら architect。scout の結論を受けて設計を決めるのはメインの仕事なので、メインが後で中身を使う調べ物は委譲せず自分で読む(上の「委譲しないもの」)。

## 損益分岐

> 委譲のブリーフを書く時間が、自分で実行する時間を上回るなら委譲しない。

委譲には固定費がかかる。ブリーフの作成(前提知識・スコープ・出力契約の書き下ろし)と、戻ってきた要約の解釈。この固定費は作業の大きさに関係なくほぼ一定なので、小さい作業ほど割に合わない。

分岐点を測る物差しは**書く量**。ブリーフより長いものを書くなら executor に書かせる。ブリーフより短い書き込み(数行の修正、一言の追記、設定値の変更)はメインでやる。

## コスト削減の順序

1. **機械的な部分とまとまった書き出しを executor へ。** タスク全体ではなく、確定している部分だけを切る。最も効くレバー。
2. **メインの effort を上げたままにしない。** 難所で `/effort high` に上げたら、終わったら medium に戻す。xhigh / max は品質差を実測した作業だけ。
3. **architect に渡すものを絞る。** 仕様を確定できる部分は確定させて executor に回し、architect には判断が残る部分だけを渡す。
4. **スコープを絞る。** 何をやらないかをユーザーと決める。

「全部 low に投げる」は手戻りで相殺されることが多い。仕様の穴は low では埋まらない。

## 長時間ランでの writer-verifier

Opus は複数サブエージェントのチームをよく統率し、writer と verifier を分ける構成が有効に働く(互いの成果を上書きする事故も少ない)。

ただしこれが効くのは**長時間・多フェーズの走行**に限る。スコープの決まった単発タスクに verifier を足すのは「自分の成果の検証」に該当して無駄になる。

長時間ランで使うなら、タスクごとではなく**間隔**で仕込む。「X ごとに、fresh context の verifier サブエージェント(architect)で成果を仕様と突き合わせる」。実装したエージェント自身に再検証させるのではなく、文脈を持たない別エージェントに照合させる。
