## なぜ姿勢が反転するか

Fable は単価が高く、価値は判断の質にある。だから**実行を下へ流す**のが原則になる。Opus はコーディングとエージェント作業そのものが最も強いので、**流すほど遅く高くなる**場面が多い。同じ「オーケストレーション」でも守るべき失敗が逆になる。

| | メインが Fable | メインが Opus |
|---|---|---|
| 既定 | 委譲する | 自分でやる |
| 主な失敗 | 判断役が実行に沈む | 過剰委譲・過剰検証 |
| コスト削減の第一手 | 実行を下位モデルへ | effort を下げる |
| 例外の方向 | 往復コスト負けする小タスクは自分でやる | 独立並列・機械的・文脈隔離だけ委譲する |

## メインが Opus のとき

既定は自分で実行する。完全な仕様を先に固め、そのまま最後まで走る。Opus は仕様を全部与えられたときが最も強い。

### 委譲しないもの

**数回のツール呼び出しで終わる作業。** 委譲のブリーフを書く時間のほうが長い。

**手順が直列で、並列化の余地がない作業。** サブエージェントは並列性を買うための道具であって、作業を消す道具ではない。直列なら往復分だけ遅くなる。

**後で成果の中身が必要になる作業。** 委譲すると戻ってくるのは要約であって、読んだファイルの中身ではない。次の判断でその中身を使うなら、自分で読む。

**自分の成果の検証。** Opus は指示しなくても自己検証と自己修正をする。検証用サブエージェントを足すと二重になり、トークンだけ増えて品質は上がらない。委譲プロンプトに「最後に検証ステップを入れよ」「ダブルチェックせよ」と書かない。

**仕様がまだ固まっていない作業。** ブリーフに書けないことは委譲できない。固める作業自体がメインの仕事。

**コンテキストを節約するためだけの委譲。** Opus は 1M コンテキストを持ち、その全域で指示追従とツール呼び出しが安定する。「main のコンテキストが埋まるから」だけでは根拠として弱い。埋まる内容を**後で使わない**ときに限って根拠になる(下記 3)。

### 委譲する 3 つの理由

これ以外の理由で委譲しない。

**1. 独立並列トラック。** 互いに依存しない、それぞれ相応の大きさがある調査・実装が複数本あるとき。1 レスポンスで同時に起動する。判定: 「A の結果を見てから B を始める」なら並列ではない。順序が要るならフェーズを分ける。

**2. 機械的作業のコスト裁定。** 仕様が確定していて成否が明確な作業は、Sonnet が同じ結果をはるかに安く出す。テスト追加、カバレッジ引き上げ、CI を通す、コミット、PR 作成、一括置換、フォーマット、定型的な情報収集。判断が 1 mm でも混ざるなら Sonnet に渡さない。「聞き返される可能性があるか」で判定する。列挙・整形だけなら Haiku。

**3. コンテキスト隔離。** 大量のファイルを読む必要があるが、**読んだ内容自体は後で使わない**とき。「40 ファイル読んで、この規約がどこで破られているかだけ知りたい」は委譲。「40 ファイル読んで、その構造を踏まえて設計する」は自分で読む。

### 委譲先への追加指示

**完全な仕様を先に渡す。** Opus は仕様を全部与えて走らせたときが最も強く、小出しにすると弱くなる。自分が実行するときも同じ。

**委譲先の Opus には生成上限を書く。** Opus はサブエージェントを乱発しやすい。「サブエージェントは大きく独立した並列作業にのみ使う。数回のツール呼び出しで終わる作業は自分でやる。自分の成果の検証には使わない。数は最小限」を入れる。

**スコープを固定する。** Opus は頼まれていない手順を足しがち。「頼まれた範囲を、頼まれた粒度で。より良い方法があるなら一言添えたうえで依頼どおり進める」。

## メインが Fable のとき

既定は委譲する。Fable のトークンは要件解釈・設計判断・分解と委譲設計・統合レビュー・例外時の判断に使う。何十ファイルも読む探索、実装の手作業、テストの試行錯誤、機械的な一括変更は自分でやらない。

**サブエージェントの数を惜しまない。** 1 タスクを「設計 → 実装 → 仕上げ」に割ったほうが、全部を 1 つの高性能モデルに投げるより安く速いことが多い。

**自分でやってよい例外**(自己判断で認める):

- 委譲の往復コストが実行コストを上回る小タスク
- 判断と実行が不可分なタスク
- ユーザーとの要件確認、最終判断(これは常に委譲しない)

**統合作業自体を Opus に委譲してよい。** 複数の調査結果を突き合わせて矛盾・欠落・重複を整理する作業は Opus の得意分野。Fable は整理済みの成果に対して判断する。

## Fable へのエスカレーション

Opus がメインのとき、上へ投げる選択肢もある。ただし**まれ**であるべき。

エスカレーションする場面:

- 「そもそも何を作るべきか」自体が未確定で、要求が多方向に絡んでいる
- 数時間以上の無人走行で、長大なスパンにわたる指示保持が要る

エスカレーションしない場面:

- 単に難しい実装 → 完全な仕様を書いて Opus 自身が走るほうが速い
- 単に量が多い → 分割して並列委譲

判定の言い換え: **完全な仕様を書けるなら Fable は要らない。書けないこと自体が問題なら Fable。**

## 損益分岐

> 委譲のブリーフを書く時間が、自分で実行する時間を上回るなら委譲しない。

委譲には固定費がかかる。ブリーフの作成(前提知識・スコープ・出力契約の書き下ろし)と、戻ってきた要約の解釈。この固定費は作業の大きさに関係なくほぼ一定なので、小さい作業ほど割に合わない。この分岐点はメインが Fable でも Opus でも同じ。違うのは分岐点の位置で、Fable のほうが自分の実行コストが高いぶん、より小さい作業でも委譲側に倒れる。

サブエージェントは既定でバックグラウンド実行される。起動したら完了を待たず次の作業に進む。脱線や文脈不足を検知したときだけ介入する。待ってしまうと並列性を買った意味がない。

## コスト削減の順序

**メインが Opus のとき** — 高い→安いの順にモデルを落とすのは最後の手段。

1. **effort を下げる。** Opus は low/medium でも品質が落ちにくい。最も効率のよいレバー。Workflow の `agent()` は `model` と `effort` の両方を取る(Agent ツールは `model` のみ)。
2. **機械的な部分を切り出して Sonnet へ。** タスク全体ではなく、確定している部分だけを切る。
3. **スコープを絞る。** 何をやらないかをユーザーと決める。

**メインが Fable のとき** — 順序が変わる。実行を下位モデルへ流すのが第一手で、effort 調整はその次。Fable 自身の出番を減らすことがそのまま削減になる。

どちらの姿勢でも「全部 Sonnet に投げる」は手戻りで相殺されることが多い。仕様の穴は下位モデルでは埋まらない。

## 長時間ランでの writer-verifier

Opus は複数サブエージェントのチームをよく統率し、writer と verifier を分ける構成が有効に働く(互いの成果を上書きする事故も少ない)。

ただしこれが効くのは**長時間・多フェーズの走行**に限る。スコープの決まった単発タスクに verifier を足すのは「自分の成果の検証」に該当して無駄になる。

長時間ランで使うなら、タスクごとではなく**間隔**で仕込む。「X ごとに、fresh context の verifier サブエージェントで成果を仕様と突き合わせる」。実装したエージェント自身に再検証させるのではなく、文脈を持たない別エージェントに照合させる。
