## 効く書き方

**理由を書く。** 依頼だけでなく「なぜそれが必要か」を書くと、受け手は書いていない細部まで目的に
沿って判断できる。`X のために Y をしたい。ついては <依頼>` の形。

**動詞で行動を指定する。** 現行モデルは指示を文字通り取る。「改善案を出せる?」は提案で止まり、
ファイルは変わらない。実装させたいなら「実装して」「直して」。逆に手を動かされたくないなら
「調査と推奨に留めて、ファイルは編集しないで」と明示する。

**適用範囲を明示する。** 一箇所の例から他へ勝手に一般化しない。「全ファイルに適用（1 つ目だけでなく）」
は冗長ではなく必須。

**禁止の列挙より、望ましい形を 1〜3 例。** 「〜しないで」の羅列は弱い。欲しい出力の形を
`<example>` タグで見せるほうが効く。多様性を持たせて 1 つの形に過学習させない。

**種類の違う内容は区切る。** 指示・背景・貼り付け材料が混ざるなら見出しか XML タグ
（`<error_log>`, `<current_code>`, `<requirements>`）で分ける。長い材料は**上部**、依頼は**末尾**。

**完了の形を書く。** 「何が出てきたら成功か」。調査依頼なら「何が分かれば答えになったか」。

**上振れが欲しいときだけ明示的に頼む。** 「関連する機能や配慮を可能な限り盛り込んで、基本の実装で
止まらないで」は効くが、全依頼に付けるとスコープが膨らむ。それが欲しい 1 箇所にだけ書く。

**成果物の長さを言う。** 現行の Opus は文書も返答も長くなりがち。文書生成を頼むなら
「内容量に見合った長さで。埋め草の節・重複する要約・定型の前置きは入れないで」。

## 入れてはいけない定型句

| 書きたくなる文 | 現行モデルで起きること | 代わりに |
|---|---|---|
| 「最後に必ず再検証して」「ダブルチェックして」 | 現行 Opus は既に自己検証する。重ねると過剰検証でトークンと時間だけ増える | 何も書かない。証跡が欲しいなら「実行したコマンドと出力を書いて」 |
| 「重要なものだけ報告して」「些末な指摘はしないで」 | 文字通り従い、同じだけ調べた上で結果を隠す。取りこぼしが増える | 「見つけたものは全部、確信度と重要度を付けて報告して」。選別は受け取ってから |
| 「思考過程を書き出して」「どう考えたか説明して」 | Fable では `reasoning_extraction` 系の拒否を踏む可能性がある | 思考ではなく根拠を求める: `path:line` の引用、コマンド出力、成果物そのもの |
| 「CRITICAL: 必ず〜しなければならない」 | 現行モデルは通常の指示で従う。強調は過剰発火を招く | 「〜して」で足りる |
| 「迷ったらツールを使って」「基本的に〜を使って」 | 過剰発火する。無条件の既定値は害 | 「理解が深まる場面では〜を使って」のように条件を付ける |
| 「3 ステップごとに進捗をまとめて」 | 既に適切な粒度で報告する。固定の足場はノイズ | 削る。形が気に入らないなら欲しい報告を 1 例見せる |
| 「必要に応じてサブエージェントを使って」 | 現行モデルは既に積極的に委譲する。grep 一回で済む調査にまで生やす | 委譲すべき条件と上限を書く。もしくは書かない |
| 手順の逐一指定 | 正解ルートが複数ある作業では、旧世代向けの過剰な手順指定は品質を下げる | 目的・制約・完了条件を書き、ルートは開ける |

## 受け手に調べさせ、考えさせる書き方

このスキルの調査は当たり付けであって、受け手の調査を省くためではない。渡した観測を鵜呑みに
させないことと、実際に手を動かして調べさせることを、プロンプト本文で担保する。

**観測として渡す**（断定しない）:

```
調査時点で観測したこと（裏取りは自分でやって、違っていたら指摘して）:
- `src/api/client.ts:88` で 3 秒のタイムアウトを設定している
- CI の失敗は `pnpm test:e2e` の 2 ケースのみ。ユニットテストは通っている
```

**推測を禁じる**（事実関係が結論を左右する依頼に）:

```
開いていないコードについて推測しないで。関連ファイルを読んでから答えて。
```

**複数仮説を要求する**（原因不明の調査依頼に）:

```
原因は特定できていない。対立する仮説を複数立てて、それぞれの確信度と、
確認に使える手段（コマンド・ログ・再現手順）を書いて。1 つに飛びつかないで。
```

**先取りした判断を明示的に開放する**:

```
以下はこちらの仮説で、決定事項ではない。より良い方針があれば、実装前にそう言って。
```

**決定事項は決定として書く**（受け手に再検討させない部分）:

```
決定事項（議論済み。前提として扱って）:
- 認証は既存の session cookie 方式を維持する。JWT への移行は今回のスコープ外
```

## 場面別に足す一文

必要な場面でだけ足す。全部載せない。

- **リポジトリを触らせる**: 「ローカルで戻せる操作（ファイル編集、テスト実行）は自由に進めて。
  戻しにくい操作や共有物に影響する操作（push、force push、ブランチ削除、外部への投稿）は
  実行前に確認して。安全チェックの迂回（`--no-verify` 等）で回避しないで」
- **過剰実装を抑える**: 「頼んだ範囲と、そのために明らかに必要な変更だけ。将来の要件を見込んだ
  抽象化・使い回しのないヘルパー・起こり得ない状況への防御は入れないで」
- **テストがある作業**: 「テストは正しさの確認手段であって仕様ではない。テストケースだけを通す
  ハードコードや回避策ではなく、一般に正しい実装をして。テスト自体が間違っていると思ったら、
  直さずにそう報告して」
- **一時ファイルを作らせる**: 「検証用に作った一時ファイルやスクリプトは、最後に片付けて」
- **長時間・複数コンテキストにまたがる**: 「進捗と残りは `progress.md` に書き足しながら進めて。
  コンテキストが尽きそうでもタスクを早めに切り上げないで、状態を保存してから続けて」
- **ヒアリングされながら進めたい**: 「不明点や大きな分岐は、進める前に AskUserQuestion で確認して」

## 完成例

### 例 1: 作業依頼（原因の当たりは付いているが断定しない）

```
E2E テストが CI で落ちていて、リリースが止まっている。原因を突き止めて直してほしい。

調査時点で観測したこと（裏取りは自分でやって、違っていたら指摘して）:
- 落ちているのは `pnpm test:e2e` の 2 ケース（`checkout.spec.ts`）。ユニットテストは通る
- ローカルでは再現しない。CI のログでは `Timeout 3000ms exceeded` が出ている
- `src/api/client.ts:88` に 3 秒のタイムアウト設定がある。先週の PR #412 で入った

タイムアウトが原因という確証はない。開いていないコードについて推測せず、関連ファイルと
CI ログを読んで自分で切り分けて。単にタイムアウト値を上げるだけの対処は避けたい。

制約: `checkout.spec.ts` のアサーションは緩めないで。テストのスキップも不可。
完了の目安: CI で `pnpm test:e2e` が緑。原因と修正内容を数行で説明できる状態。
```

### 例 2: 設計・計画（判断を委ねる）

```
社内向けの管理画面に「通知設定」を追加したい。設計から相談したい。

背景: ユーザーは 200 人程度の社内利用。通知はメールと Slack の 2 経路で、
イベント種別ごとに on/off を切り替えたい。頻度の制御は今回は不要。

決定事項（前提として扱って）:
- 認証は既存の session cookie 方式を維持する。JWT 移行は今回のスコープ外
- 保存先は既存の PostgreSQL

以下はこちらの仮説で、決定ではない: 設定はユーザー単位の JSON カラムで持つのが早いのでは、
と考えている。より良い方針があれば実装前にそう言って。

まずコードベースを読んで、既存の設定系機能（あるなら）の作りと命名の慣習を確認してから、
データモデルと画面構成の案を 2〜3 個、それぞれのトレードオフ付きで出して。推奨も添えて。
この段階ではファイルを編集しないで。方針が決まってから実装に入りたい。
```

### 例 3: 相談・壁打ち（編集させない）

```
記事の下書きが読みづらいと感じているが、どこが悪いのか自分で言語化できていない。相談したい。

対象は `articles/rag-tuning.md`。技術記事で、読者は RAG を触ったことがあるエンジニア。
文字数は変えたくない（今 6000 字程度）。

まず記事を読んで、読みづらさの原因の仮説を複数立てて、確信度を付けて挙げて。
構成の問題か、文の問題か、前提説明の量か、切り分けたい。
その上で、どこから直すのが効果的か推奨を出して。この段階ではファイルを編集しないで。
議論して方針が固まってから直したい。
```
