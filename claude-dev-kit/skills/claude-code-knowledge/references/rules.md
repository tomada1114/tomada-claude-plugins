# Rules（ルール）

> CLAUDE.mdを補完する、モジュール化されたトピック別指示ファイル。パス指定で特定ファイルにのみ適用可能。

## CLAUDE.md肥大化問題

CLAUDE.mdは便利な機能ですが、プロジェクトが成長するにつれて内容が肥大化していきます。コーディング規約、テストの書き方、API設計のルール、セキュリティ要件...と書き込んでいくうちに、管理が大変になります。

問題は、**CLAUDE.mdの内容は起動時に全てコンテキストに読み込まれる**ことです。TypeScriptのルールも、Markdownのルールも、APIのルールも、全部がコンテキストを占有してしまいます。

「必要な時だけ、必要なルールを読み込んでほしい」

そんなニーズに応えるのが`.claude/rules/`機能です。

## Rulesとは

Rulesは、`.claude/rules/` ディレクトリに配置されたモジュール化されたトピック別の指示ファイルです。大規模プロジェクト向けに、1つの大きなCLAUDE.mdファイルを複数の小さなルールファイルに分割する仕組みです。

CLAUDE.mdがプロジェクト全体に適用される「全店共通マニュアル」なら、Rulesは特定の売り場に入った時だけ適用される「売り場別ルール」のようなものです。

### コンビニで例えると：売り場別ルール

コンビニでは売り場ごとに異なるルールがあります。ホットスナックコーナーでは「調理時間を記録する」「廃棄時間を守る」、レジでは「年齢確認必須商品に注意」「ポイントカードを確認」など、担当する売り場によって適用されるルールが変わります。

そこで、各売り場に**売り場別ルール**を掲示することにしました：

```
------- ホットスナックコーナーのルール -------
# ホットスナック担当ルール
揚げ物・中華まんなどの調理・販売を担当します。

## 必須作業
- 調理開始時刻を記録すること
- 廃棄時間を厳守すること

## 注意事項
- からあげクン: 調理後4時間で廃棄
- 中華まん: 温度管理を徹底
---------------------------------
```

売り場別ルールを掲示しておけば、店員はその売り場に入るときに自動でルールを確認します：

```
店長: 「ホットスナックの補充お願い」

店員: (ホットスナックコーナーのルールを確認)
店員: 「調理時刻を記録して...廃棄時間もチェックします」
店員: 「からあげクン、補充完了しました！」
```

**売り場ごとの注意事項を、自動で守ってくれるようになりました！**

## Rulesのポイント

- 特定のエリア（ファイルパス）に適用されるルール
- そのエリアに入ったときだけ自動で読み込まれる（他のエリアのことは忘れていい）
- 仲間（エージェント）に毎回伝えなくていい
- **pathsなし**の場合、すべてのファイルに無条件で適用

## Rulesの場所

### プロジェクトレベル

Rulesは `.claude/rules/` ディレクトリに配置します。サブディレクトリも使えます：

```
.claude/rules/
├── code-style.md      # コードスタイルガイドライン
├── testing.md         # テスト規約
├── security.md        # セキュリティ要件
├── frontend/
│   ├── react.md
│   └── styles.md
└── backend/
    ├── api.md
    └── database.md
```

### ユーザーレベル

`~/.claude/rules/` にルールを配置すると、すべてのプロジェクトに適用されます。プロジェクトルール（`.claude/rules/`）より優先度が低い。

## Rulesの形式

各ルールファイルは、YAMLフロントマターでパスを指定します：

```markdown
---
paths: src/components/**
---

# フロントエンド開発ルール

## 使用技術
- React + TypeScript
- Tailwind CSSでスタイリング

## コンポーネント設計
- 1ファイル1コンポーネント
- Propsは型定義必須
```

### 設定フィールド

| フィールド | 必須 | 説明 |
|:---------|:----|:-----|
| `paths` | **任意** | ルールが適用されるファイルパターン（glob形式）。省略時はすべてのファイルに適用 |

### Globパターンの詳細

| パターン | マッチ対象 |
|---------|-----------|
| `**/*.ts` | 任意のディレクトリ内のすべてのTypeScriptファイル |
| `src/**/*` | `src/` ディレクトリ以下のすべてのファイル |
| `*.md` | プロジェクトルートのMarkdownファイル |
| `src/components/*.tsx` | 特定ディレクトリのReactコンポーネント |

**ブレース展開（複数パターン）:**
```yaml
paths: src/**/*.{ts,tsx}
```

**複数パターン（カンマ区切り）:**
```yaml
paths: {src,lib}/**/*.ts, tests/**/*.test.ts
```

## 実用的な例

### フロントエンドルール

```markdown
---
paths: src/components/**
---

# フロントエンド開発ルール

## 使用技術
- React + TypeScript
- Tailwind CSSでスタイリング

## コンポーネント設計
- 1ファイル1コンポーネント
- Propsは型定義必須
- カスタムフックは `use` プレフィックス
```

### バックエンドルール

```markdown
---
paths: src/api/**
---

# バックエンドAPI開発ルール

## 使用技術
- Express.js
- Prisma ORM

## API設計
- RESTful原則に従う
- エラーレスポンスは統一フォーマット
- 認証が必要なエンドポイントは middleware で保護
```

### テストルール

```markdown
---
paths: tests/**
---

# テストコード規約

## テストフレームワーク
- Jest + React Testing Library

## 命名規則
- テストファイル: `*.test.ts` または `*.spec.ts`
- describe: 機能名
- it: 「〜すべき」形式

## カバレッジ
- 最低80%を目標
```

## CLAUDE.md と Rules の使い分け

| 機能 | スコープ | 使うとき |
|:-----|:--------|:--------|
| **CLAUDE.md** | プロジェクト全体 | 常に適用される設定やルール（世界観） |
| **Rules** | 特定のパス | パスごとに異なる設定やルール（エリアの看板） |

### 判断基準

- **プロジェクト全体で守るべきルール** → CLAUDE.md
  - 例: 技術スタック、コーディング規約、命名規則
- **特定のディレクトリでのみ守るべきルール** → Rules
  - 例: フロントエンド固有のルール、API設計規約、テスト規約

## 適用のタイミングと挙動

### 動的読み込み（Dynamic Loading）

Rulesの最大の特徴は、**必要な時だけ動的に読み込む**ことでコンテキストを節約できる点です。

| ルール種別 | 読み込みタイミング | コンテキスト消費 |
|:---------|:-----------------|:---------------|
| `paths`なし | セッション開始時 | 常に消費 |
| `paths`あり | マッチするファイル編集時 | 必要な時だけ |

### 動的読み込みの挙動

- **初回アクセス**: 対象ファイルを編集するとルールが動的に読み込まれる
- **重複防止**: 同じルールは再度読み込まれない（コンテキスト効率◎）
- **複数ルールの同時適用**: パスが重複する場合、すべてのマッチしたルールが累積で適用（TypeScript + APIルールなど）

### 動的ロードの確認

実際にファイルを読み込むと、以下のようにルールが動的にロードされる様子が確認できます:

```
⏺ Read(src/components/Button.tsx)
  ⎿  Read 15 lines
  ⎿  .claude/rules/frontend.md   ← ここで動的ロード！
```

一度ロードされたルールは、同じセッション内で再度ロードされることはありません。

### 設定の確認方法

**現在読み込まれているルールの確認（/memory）**

```bash
/memory
```

このコマンドを実行すると、以下のような選択画面が表示されます:

```
╭──────────────────────────────────────────────────────────────────╮
│ Select memory to edit:                                           │
│                                                                  │
│    1. User memory                Saved in ~/.claude/CLAUDE.md    │
│    2. .claude/CLAUDE.md                                          │
│  ❯ 3. .claude/rules/general.md                                   │
│    4. Project memory             Saved in ./CLAUDE.md            │
╰──────────────────────────────────────────────────────────────────╯
```

`paths` 指定がないルールファイルは常に表示されます。

**コンテキスト効率の確認（/context）**

```bash
/context
```

動的に読み込まれたルールによるコンテキスト増加を確認できます。

### 注意点

- 動的に読み込まれたルールは `/memory` には表示されないが、実際には適用されている
- これはバグではなく仕様

### 優先度

1. プロジェクト固有ルール（`.claude/rules/`）が最優先
2. ユーザーレベルルール（`~/.claude/rules/`）はその次

## ベストプラクティス

1. **ルールを焦点化**: 各ファイルは1つのトピック（`testing.md`、`api-design.md` など）をカバー
2. **記述的なファイル名**: ファイル名がカバー内容を示すこと
3. **条件付きルール（`paths`）は控えめに**: パス指定は本当に特定ファイル型にのみ適用すべき場合のみ
4. **サブディレクトリで組織化**: 関連ルールをグループ化（例：`frontend/`、`backend/`）
5. **重複を避ける**: CLAUDE.md と重複する内容は書かない
6. **チームで共有**: `.claude/rules/` をGitで管理

### シンボリックリンクのサポート

```bash
# 共有ルールディレクトリのシンボリックリンク
ln -s ~/shared-claude-rules .claude/rules/shared

# 個別ルールファイルのシンボリックリンク
ln -s ~/company-standards/security.md .claude/rules/security.md
```

円形シンボリックリンクは自動的に検出・処理されます。

## まとめ表

| 機能 | コンビニでの例え | 定義するもの | 使うとき |
|:-----|:---------------|:------------|:--------|
| **CLAUDE.md** | 全店共通マニュアル | 前提条件 | 常に適用される設定やルール |
| **Rules** | 売り場別ルール | パス別の前提 | パスごとに異なる設定やルール |
| **Command** | レジの定型フレーズ | 何をやるか | よく使う指示をまとめたい |
| **Skill** | バックヤードのマニュアル棚 | どうやるか | 複雑な手順・知識を定義したい |
| **Subagent** | 本部サポートセンター | どんな専門家か | 委託したい/並列実行したい |
