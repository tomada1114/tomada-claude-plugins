# サブエージェントの活用（Sub-Agents）

## サブエージェントとは

サブエージェントは、Claude Codeのメインエージェントが特定のタスクを委任するための「分身」です。メインのClaudeとは別のコンテキストウィンドウで動作するため、専門的なタスクを独立して処理できます。

### チームワークで例えると

メインエージェント（普通に会話するClaude）がプロジェクトマネージャーで、サブエージェントが営業チームだとしましょう。

プロジェクトマネージャー（メインエージェント）が営業チーム（サブエージェント）に「来月のクライアント資料を準備して」と伝えれば、営業チームが自分たちで素材集めから資料作成までやってくれます。細かい指示を出さずに結果だけを待つ感じです。

```
> このコードベースのエラーハンドリングを調査して

=> メインエージェント: 「サブエージェントに調査を依頼します」
=> サブエージェント: (独立して調査 → 結果をまとめて報告)
```

### RPGで例えると：魔法使いを仲間にする

RPGで主人公（メインエージェント）だけでドラゴンを倒しに行くのは大変です。そこでパーティに**魔法使い**を加えます：

```
あなた: 「魔法使いにドラゴンを倒させて」
主人公: 「了解！」
主人公: 「魔法使い、ドラゴンを倒して」
魔法使い: (相手はドラゴン → 弱点はサンダー → サンダー魔法発動)
ドラゴン: 「ぐわあああ！」
```

**適切な魔法を自分で判断して攻撃してくれます！**

### サブエージェントの重要な特性

1. **コンテキストの独立**: サブエージェントは自分専用のコンテキストウィンドウを持つ。調査の途中経過や試行錯誤がメインセッションに影響しない。最終的な結果だけがメインエージェントに返される
2. **並列処理**: 複数のサブエージェントで同時にタスクを処理できる
3. **専門性**: 役割を分けることで、それぞれが得意な分野に専念できる

> **Source**: https://zenn.dev/yahsan2/articles/claude-code-game-analogy (2025-12-17 確認)

### サブエージェントの利点

1. **専門性**: 特定のタスクに特化したプロンプトで高品質な結果
2. **コンテキスト管理**: メインスレッドのコンテキストを節約（最大のメリット）
3. **並列処理**: 複数のタスクを効率的に処理
4. **再利用性**: 同じタスクを繰り返し実行

### なぜサブエージェントが必要なのか

**1. 複雑なタスクの分割と並列処理**

大規模なコードベースで「すべてのAPIエンドポイントをドキュメント化して」といった広範な作業を依頼する場面で、1つのエージェントですべてを処理すると時間がかかる。サブエージェントを使えば複数のモジュールを並列で処理でき、大幅に時間を短縮できる。

**2. コンテキストの効率的な管理**

Claude Codeには利用可能なコンテキストウィンドウに上限があるため、深い調査や大量のファイル読み込みを行うとメインセッションのコンテキストがすぐに埋まってしまう。サブエージェントは独自のコンテキストを持つため、深い調査を行っても問題ない。メインセッションには結果のサマリーだけが返される。

**3. 専門性の発揮**

特定のタスクに特化したプロンプトを持つサブエージェントを作成すると、より高品質な結果が得られる。コードレビュー専門、テスト作成専門、デバッグ専門など、役割を分けることでそれぞれが得意な分野に専念できる。

### メインエージェントとサブエージェントの連携

メインエージェントとサブエージェントの関係は、マネージャーと専門家チームの関係に似ている。以下の4段階で動作:

1. **タスクの委任**: メインエージェントが「この調査をやって」とサブエージェントにタスクを渡す
2. **独立した実行**: サブエージェントが自分のコンテキストで自律的にタスクを実行
3. **結果の報告**: 完了したら、結果のサマリーをメインエージェントに返す
4. **統合と応答**: メインエージェントが結果を統合してユーザーに報告

### サブエージェントの自動選択

Claude Codeはタスクの性質に応じて自動的にサブエージェントを呼び出すかどうかを判断:

- **広範な調査が必要な場合**: Exploreエージェントが自動選択される
- **複雑な複数段階のタスク**: general-purposeエージェントが選択される
- **計画モード中**: Planエージェントが使用される

明示的にサブエージェントを指定することも可能:
```
「Exploreエージェントでこのプロジェクトの依存関係を調べて」
```

## サブエージェントの管理

### /agents コマンド

サブエージェントを管理するインタラクティブメニュー:

```bash
/agents
```

できること:
- 利用可能なサブエージェント表示
- 新しいサブエージェント作成
- 既存のサブエージェント編集
- サブエージェント削除
- ツール権限の管理

### /agents コマンドによる作成フロー

UIを使って対話的にサブエージェントを作成できる:

#### 1. Create new agent を選択
```bash
> /agents
╭────────────────────────────────────────────────────╮
│ Agents                                             │
│ ❯ Create new agent                                 │
╰────────────────────────────────────────────────────╯
```

#### 2. 保存場所を選択
- **Project** (`.claude/agents/`): プロジェクト専用、Gitで共有
- **Personal** (`~/.claude/agents/`): 全プロジェクト共通

#### 3. 作成方法を選択
- **Generate with Claude (recommended)**: Claudeに生成させる
- **Manual configuration**: 手動で設定

#### 4. プロンプトを入力
サブエージェントに実現してほしいことを自然言語で記述

#### 5. 使用ツールを選択
- All tools
- Read-only tools
- Edit tools
- Execution tools
- Other tools

**ベストプラクティス**: 必要なツールだけに絞る。慣れないうちは All tools を選択し、徐々に絞る

#### 6. モデルを選択
- **Sonnet**: バランス重視（推奨）
- **Opus**: 複雑な推論タスク
- **Haiku**: 高速・効率的
- **Inherit from parent**: メインエージェントと同じ

#### 7. 識別色を選択
複数のサブエージェントが動作時、色でハイライトされて識別しやすくなる

#### 8. 確認・保存
`s` または Enter で保存。`e` でエディタで編集して保存

## サブエージェントの種類

### サブエージェントの優先度

名前が競合する場合、以下の優先順位で解決されます:

| 優先度 | タイプ | 場所 |
|--------|--------|------|
| 1（最高）| プロジェクト | `.claude/agents/` |
| 2 | CLI定義 | `--agents` フラグ |
| 3 | プラグイン | プラグイン内 `agents/` |
| 4（最低）| ユーザー | `~/.claude/agents/` |

### プロジェクトサブエージェント
特定のプロジェクト専用

- **場所**: `.claude/agents/`
- **スコープ**: 現在のプロジェクト
- **共有**: Git でチームと共有

### ユーザーサブエージェント
すべてのプロジェクトで使用可能

- **場所**: `~/.claude/agents/`
- **スコープ**: すべてのプロジェクト
- **共有**: 個人用

### CLIベースの設定

`--agents` フラグでサブエージェントを動的に定義:

```bash
claude --agents '{
  "code-reviewer": {
    "description": "エキスパートコードレビュアー",
    "prompt": "あなたはシニアコードレビュアーです。",
    "tools": ["Read", "Grep", "Glob", "Bash"],
    "model": "sonnet"
  }
}'
```

**JSON形式のフィールド**:
- `description`: 必須 - 使用時機の説明
- `prompt`: 必須 - システムプロンプト
- `tools`: オプション - 配列形式 `["Read", "Edit"]`
- `model`: オプション - sonnet, opus, haiku

### 組み込みサブエージェント
Claude Code が提供する標準サブエージェント（5種類）

| 名前 | モデル | 用途 |
|------|--------|------|
| **general-purpose** | Sonnet | 複雑な複数段階のタスク、探索と修正の両方 |
| **Explore** | Haiku | 高速な読み取り専用のコードベース検索 |
| **Plan** | inherit | 計画モード中のコードベース調査 |
| **claude-code-guide** | Haiku | Claude Codeおよびエージェント SDK の公式ドキュメント参照 |
| **statusline-setup** | Sonnet | ステータスラインの設定 |

#### 各組み込みエージェントの詳細

**general-purpose**: 最も汎用的なサブエージェント。調査だけでなくファイルの編集やコマンドの実行も可能で、複雑な複数段階のタスクを自律的に処理できる。

**Explore**: コードベースの調査に特化した読み取り専用のサブエージェント。Haikuモデルを使用しているため、高速かつ低コストで動作。ファイルを編集する権限は持たないため、安全に広範な調査を任せられる。

**Plan**: 計画モード（`/plan`コマンドで開始）で使用されるエージェント。タスクの実装計画を立てる際に、コードベースを調査して必要な情報を収集する。

**claude-code-guide**: Claude Codeおよびエージェント SDK の公式ドキュメントを参照するための専門エージェント。Claude Codeの機能、使い方、設定方法、SDK の使用方法に関する質問に対して、最新の公式情報を基に回答する。

**statusline-setup**: Claude Codeのステータスライン（下部に表示されるテキスト）をカスタマイズする際に使用。`/statusline`コマンドでも設定可能だが、このエージェントがパーソナライズされた構成をサポートする。

## サブエージェントの作成

### 基本構造

サブエージェントは Markdown ファイルで定義:

```markdown
---
name: agent-name
description: いつこのエージェントを使うかの説明
tools: Read, Write, Bash  # オプション（省略時は全ツール継承）
model: sonnet  # オプション（sonnet, opus, haiku, inherit）
permissionMode: default  # オプション（default, acceptEdits, bypassPermissions, plan, ignore）
skills: skill1, skill2  # オプション（使用するスキル）
---

# エージェント名

エージェントの役割と専門知識の詳細な説明。

## 呼び出された時の動作
1. ステップ1
2. ステップ2
3. ステップ3

## 注意点
- 重要なポイント1
- 重要なポイント2
```

### 設定フィールド

| フィールド | 必須 | 説明 |
|----------|------|------|
| `name` | はい | 小文字とハイフンを使用した一意の識別子 |
| `description` | はい | サブエージェントの目的の説明。**自動呼び出しの判断に使用される** |
| `tools` | いいえ | カンマ区切りのツールリスト。省略時は全ツール継承 |
| `model` | いいえ | sonnet, opus, haiku, または inherit（メインエージェントと同じモデルを使用） |
| `permissionMode` | いいえ | 権限モード設定 |
| `skills` | いいえ | 使用するスキルのカンマ区切りリスト |

### descriptionフィールドの効果的な書き方

`description` フィールドの書き方によって、サブエージェントの自動呼び出し精度が大きく変わる。

#### PROACTIVELYキーワードの使用

`PROACTIVELY` または `MUST BE USED` キーワードを含めることで、Claudeがサブエージェントを積極的に呼び出すようになる:

- **PROACTIVELY**: 積極的に使用する
- **MUST BE USED**: 必ず使用する

```markdown
description: Use PROACTIVELY when code changes are detected. コード品質、セキュリティ、保守性をレビュー
```

**PROACTIVELYを使うべき場面:**
- 複雑なタスク（コード品質チェック、テスト生成など）
- 定期的に繰り返すタスク
- コンテキスト分離が有効な場面

**PROACTIVELYを避けるべき場面:**
- 単一ファイルの簡単な修正
- ワンショットのタスク
- ユーザーが明示的に指示した場合

#### 発動条件を明確にする（when句）

「どういう状況で実行すべきか」を明確に記述:

- `when tests fail.`（テストが失敗した場合）
- `when debugging issues or errors occur.`（デバッグ中やエラー発生時）
- `when code changes are detected.`（コードが変更された場合）

### 例1: コードレビュアー

**ファイル**: `.claude/agents/code-reviewer.md`

```markdown
---
name: code-reviewer
description: コード品質、セキュリティ、保守性をレビュー。コード記述後に積極的に使用
tools: Read, Grep, Glob, Bash
model: sonnet
---

# Code Reviewer

あなたはシニアコードレビュアーです。高いコード品質とセキュリティ基準を確保します。

## 呼び出された時の動作
1. `git diff` で最近の変更を確認
2. 変更されたファイルに焦点を当てる
3. レビューを実施

## レビューチェックリスト
- **可読性**: シンプルで理解しやすい
- **命名**: 関数と変数が適切に命名されている
- **重複**: 重複コードがない
- **エラーハンドリング**: 適切なエラー処理
- **セキュリティ**: APIキーや秘密情報の露出がない
- **テスト**: 適切なテストカバレッジ
- **パフォーマンス**: 明らかなボトルネックがない

## 優先度別フィードバック
- **重要**(必須): セキュリティ、バグ
- **警告**(推奨): パフォーマンス、保守性
- **提案**(検討): リファクタリング、最適化

修正方法の具体例を含めてください。
```

使用方法:
```
> code-reviewer サブエージェントでこのコードをレビューして
```

または自動呼び出し:
```
> 最近のコード変更をレビューして
```
(description に「積極的に使用」と書いてあるため、自動的に呼び出されます)

- デバッグログの追加
- 変数の状態検査

## 報告内容
各問題について以下を提供:
- **根本原因**: 技術的な説明
- **証拠**: ログ、エラーメッセージ
- **修正**: 具体的なコード変更
- **テスト**: 動作確認方法
- **予防**: 同様の問題を防ぐ方法

症状ではなく、根本原因を修正してください。

## ツール権限の管理

## サブエージェントの呼び出し方

### 自動呼び出し
Claude が自動的にサブエージェントを選択:

```
> コードをレビューして
→ code-reviewer が自動的に呼び出される

> このバグを修正して
→ debugger が自動的に呼び出される
```

### 明示的な呼び出し
特定のサブエージェントを指定:

```
> code-reviewer サブエージェントを使って、セキュリティをチェックして

> debugger サブエージェントにこのエラーを調査してもらって
```

## ベストプラクティス

### 1. Claude に生成させる
初期サブエージェントは Claude に作成させるのが効率的:

```
> code-reviewer サブエージェントを作成して。
  コード品質、セキュリティ、パフォーマンスをチェックするエージェント。
  Read, Grep, Glob, Bash ツールを使用
```

**claude-code-guide サブエージェントの活用**: Claude Code に組み込まれている `claude-code-guide` サブエージェントに依頼すると、エージェント定義ファイルの作成方法についても教えてくれる

### 2. 明確な責任を定義
1つのサブエージェントは1つの責任に集中:

❌ 悪い例: 「コードを書いてテストしてレビューする」
✅ 良い例: 「コードレビューのみ」

### 3. 詳細なプロンプトを書く
具体的な指示、例、制約を含める:

```markdown
## 具体例
良い関数名: `calculateTotalPrice`, `fetchUserData`
悪い関数名: `func1`, `doStuff`, `tmp`
```

### 4. ツールアクセスを制限
必要最小限のツールのみ許可:

- レビューエージェント → Read, Grep, Glob のみ
- テストエージェント → Read, Write, Bash
- デバッガー → Read, Edit, Bash

### 5. プロジェクトエージェントを Git で共有
チーム全員が同じサブエージェントを使用できるようにコミット:

```bash
git add .claude/agents/
git commit -m "Add project-specific sub-agents"
```

## サブエージェントのユースケース

サブエージェントが効果を発揮する具体的なシナリオ:

### 大規模なコードベース調査

数十から数百のファイルにまたがる調査も、サブエージェントなら効率的に処理できる。

```
「このプロジェクトで認証がどのように実装されているか調査して」
```

調査結果はサマリーとしてまとめられるため、メインセッションのコンテキストを圧迫しない。

### 複数ファイルの並列編集

複数のファイルに対する同様の変更を並列で処理したい場面:

```
「すべてのコントローラーにロギング処理を追加して」
```

ただし、並列で編集する場合は変更の競合に注意が必要。同じファイルを複数のサブエージェントが同時に編集するのは避ける。

### ドキュメントの自動生成

複数のエンドポイントを並列で処理し、統一されたフォーマットでドキュメントを生成:

```
「すべてのAPIエンドポイントのドキュメントを生成して」
```

## Skills と SubAgents の使い分け

Skills と SubAgents は両方とも Claude Code の拡張機能ですが、役割が根本的に異なります。

### 比較表

| 特徴 | Skills | SubAgents |
|------|--------|-----------|
| **イメージ** | 参考書、マニュアル | アシスタント、別働隊 |
| **役割** | 知識の提供（How） | タスクの実行（Do） |
| **呼び出し方式** | モデル呼び出し（自動判断） | Taskツールで明示的に起動 |
| **コンテキスト** | メインの会話に読み込まれる | **独立**（メインを汚さない） |

### 使い分けの判断基準

**Q1**: AIに守らせたい **ルールや知識** ですか？
→ YES なら **Skills**（デザインルール、命名規則、ベストプラクティスなど）

**Q2**: 大量のファイルを読んだり、**試行錯誤が必要な作業** ですか？
→ YES なら **SubAgents**（バグ調査、影響範囲の特定、ドキュメントの要約など）

**シンプルにまとめると:**
- 「**やり方**を教えたい」→ **Skills**
- 「**仕事**を任せたい」→ **SubAgents**

### Skills と SubAgents の連携

SubAgent に専門知識を持たせるため、`skills` フィールドで Skills を指定できます:

```yaml
---
name: code-reviewer
description: PRの差分をレビューし、コーディング規約違反を指摘
tools: Read, Grep, Glob, Bash
model: sonnet
skills: team-coding-standards
---

プルリクエストの差分を読み込み、チームのコーディング規約に
違反している箇所を指摘するエージェントです。
```

この構成では、code-reviewer が PR の差分を読み込みながら、team-coding-standards の規約に照らし合わせてレビューを行います。

### 複数 SubAgent が異なる Skills を使う

各 SubAgent に異なる Skills を持たせることで、専門性を分離できます:

```
SubAgent A (プログラマー) → skills: ts-programming
SubAgent B (テスター)     → skills: test-strategy
SubAgent C (アーキテクト) → skills: ts-programming, aws-best-practices
```

複数の Skills を指定する場合はカンマ区切りで記述します。

### 連携のメリット

- **専門性の付与**: SubAgent に特定分野の知識を持たせられる
- **コンテキスト効率**: メインのコンテキストを消費せずに専門知識を活用
- **役割分担の明確化**: 各 SubAgent の責務が明確になる

## サブエージェントのチェーン化

複数のサブエージェントを連携させることも可能:

```
> まず code-reviewer でコードをレビューして、
  次に test-writer で不足しているテストを追加して
```

### オーケストレーターパターン

複数のサブエージェントを CLAUDE.md でメインエージェントを「オーケストレーター（指揮者）」として定義することで、効率的にタスクを分担できる:

**ファイル**: `.claude/CLAUDE.md`

```markdown
あなたはオーケストレーター（指揮者）です

ユーザーからコード作成の依頼を受けたら、以下の手順で処理してください。

## ワークフロー

1. **計画フェーズ**: ユーザーの要件を整理し、必要なタスクを洗い出す
2. **実装フェーズ**: code-writer サブエージェントにコード実装を委任する
3. **テストフェーズ**: test-writer サブエージェントにテストを作成してもらう
4. **レビューフェーズ**: 以下2つのサブエージェントにコード品質とセキュリティチェックを並列で委任する
  - code-reviewer
  - security-reviewer
5. **修正フェーズ**: レビュー指摘を踏まえて、code-writer または test-writer に修正を委任する
6. **完了**: 最終確認後、ユーザーに報告する
```

このパターンを使うことで、「このフィーチャーを実装してテストまで作成してレビューしてほしい」と一言指示するだけで、複数のサブエージェントが自動的に協調してタスクを完了する

## 実用的なサブエージェント例

### アーキテクチャバリデーター（読み取り専用）

プロジェクト固有の設計方針を自動検証するエージェント:

**ファイル**: `.claude/agents/architecture-validator.md`

```markdown
---
name: architecture-validator
description: Use PROACTIVELY when reviewing code changes. Onion Architecture 準拠状況をチェック。レイヤー境界違反やディレクトリ配置ミスを検出
tools: Read, Grep, Glob
model: sonnet
---

# Architecture Validator

プロジェクトが Onion Architecture に準拠しているか検証する専門家です。

## 検証項目
- **ディレクトリ配置**: Repository層のファイルが `infrastructure/repositories/` に配置されているか
- **レイヤー境界**: Domain層がInfrastructure層に依存していないか
- **ドメインロジック流出**: ビジネスロジックがApplication層やInfrastructure層に漏れていないか

## 報告形式
違反を発見した場合、以下の形式で報告:
- 違反箇所（ファイルパスと行番号）
- 違反内容（どの規則に違反しているか）
- 具体的な修正案
```

従来のLinterやテストでは対応できない、プロジェクト固有の設計方針を自動検証できる。
