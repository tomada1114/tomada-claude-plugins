# とまだ式基本文法ルール

**Version**: 1.3.0
**Last Updated**: 2026-01-23

このドキュメントは、すべての「とまだ式」コンテンツに共通する基本的な文法ルールを定義します。

---

## 一文の長さ

### 基本原則

**推奨**: 40-60文字程度（自然な長さ）
**許容**: 80文字程度まで
**要分割**: 80文字を超える場合は2文に分割を検討

### 重要な考え方

- 短くすることが目的ではなく、**自然なテンポで読める**ことが重要
- 無理に短く区切って接続詞を連発すると、かえって機械的になる
- 内容的に一つのまとまりなら、60文字程度でも1文にする方が自然

### 評価基準

**優（14-15点）**:
- 大半の文が自然な長さで読みやすい
- 80文字を超える文がない、または1-2個程度
- 長すぎる文は適切に分割されている

**良（11-13点）**:
- 大半の文が適切な長さだが、長い文が散見される
- 80文字を超える文が3-5個程度

**可（7-10点）**:
- 長い文が目立つ（80文字超が6-10個）
- 読みにくさを感じる部分がある

**不可（0-6点）**:
- 多くの文が長すぎる（80文字超が11個以上）
- 一文が複雑で理解しづらい

## 段落の長さ

### 基本原則

**推奨**: 10行以内
**区切り**: 意味的にまとまった文のグループごと
**改行**: 段落間は改行2つ

### ガイドライン

- 1つの段落には1つのトピック
- 段落が長くなりすぎる場合は、見出しの追加を検討
- 視覚的な読みやすさを重視

### 例

✅ **良い例**:
```markdown
Gitは、変更履歴を記録してくれる便利なツールです。コードを書いている途中で、「さっきの状態に戻したい」と思ったことはありませんか？Gitを使えば、いつでも過去の状態に戻ることができます。

Gitの仕組みは、ゲームのセーブポイントに似ています。重要な変更の前にコミット（記録）しておけば、失敗しても安心です。
```

❌ **悪い例**（長すぎる段落）:
```markdown
Gitは、変更履歴を記録してくれる便利なツールです。コードを書いている途中で、「さっきの状態に戻したい」と思ったことはありませんか？Gitを使えば、いつでも過去の状態に戻ることができます。Gitの仕組みは、ゲームのセーブポイントに似ています。重要な変更の前にコミット（記録）しておけば、失敗しても安心です。さらに、Gitを使うと複数人での開発がしやすくなります。それぞれが独立して作業しながら、最後に統合することができるのです。
```

## 見出し構成

### メイン見出し（H2: ##）

**記事（Qiita/Zenn）**: 4-7個
**書籍（Zenn Book）**: 5-8個（「学習の目標」「はじめに」「まとめ」を含む）

### サブ見出し（H3: ###）

- 見出し階層は論理的に
- メイン見出しの下に複数のサブ見出しを配置可能

### 太字（**）ではなくH3見出しを使うべき場合

太字で擬似的な見出しを作る場面があるが、以下の場合は**H3見出しを使う**こと：

| 条件 | 推奨 |
|------|------|
| 前後に説明文がある | H3見出し |
| 箇条書きが複数行になる | H3見出し |
| 同レベルの項目が2つ以上ある | H3見出し |
| 1行の簡潔なラベルのみ | 太字でもOK |

**✅ 推奨パターン（H3見出し）**
```markdown
## 私の使い分け方針

個人的には、以下のように使い分けています。

### 旧形式を使う場合

明示的に呼び出す意図が強いものを配置しています。

- 項目1
- 項目2

### 新形式を使う場合

Claude Code に判断を委ねたいものを配置しています。

- 項目1
- 項目2
```

**❌ 避けるべきパターン（太字で代用）**
```markdown
## 私の使い分け方針

**旧形式を使う場合**

明示的に呼び出す意図が強いものを配置しています。

- 項目1
- 項目2
```
→ 前後に説明文があり、複数項目があるならH3見出しが適切

### H4見出し（####）

- 3段落以上の内容がある場合のみ使用
- 深すぎる階層は避ける（H5以降は使用しない）

### 見出しの長さ

**推奨**: 30文字以内
**原則**: 簡潔で明確に

## 数字での体系化（追加ルール）

複数の項目を説明する際は、**数字で整理する**ことで読者の理解を助ける。

### 基本原則

読者は「あと何個あるのか」が分かると安心して読み進められる。

| パターン | 例 |
|---------|-----|
| **数を予告** | 「3つのポイントがあります」 |
| **番号付け** | 「1つ目は〜、2つ目は〜」 |
| **見出しに数字** | 「## 3つの注意点」 |

### ✅ 推奨パターン

```markdown
## Gitを使う3つのメリット

Gitを使うことで、以下の3つのメリットがあります。

### 1. 変更履歴を追跡できる

コードの変更履歴を自動で記録してくれます。

### 2. 過去のバージョンに戻せる

失敗しても、いつでも過去の状態に戻れます。

### 3. 複数人で並行して開発できる

ブランチ機能を使えば、独立して作業できます。
```

### ❌ 避けるべきパターン

```markdown
## Gitを使うメリット

Gitを使うことで、いくつかのメリットがあります。

### 変更履歴を追跡できる
### 過去のバージョンに戻せる
### 複数人で並行して開発できる
```

→ 「いくつか」ではなく具体的な数字を使う

### 数字の使い方ガイド

| 項目数 | 推奨 |
|-------|------|
| 2個 | 「2つの〜」または「〇〇と△△」 |
| 3-5個 | **最も効果的**。「3つの〜」「5つのステップ」 |
| 6-7個 | 「7つの〜」でも可だが、グループ化を検討 |
| 8個以上 | カテゴリに分けて整理する |

## 見出しと本文の関係

### 重要な原則

1. **見出しの直後には必ず説明文を配置**
2. **見出し→箇条書きは避ける**
3. **見出しの直前に予告文は不要**
4. **説明文は「その見出しの内容を説明」するもの**

### ❌ 避けるべきパターン

**パターン1: 見出し直後に箇条書き**
```markdown
## Gitのメリット

- 変更履歴を追跡できる
- 複数人での開発がしやすい
- 過去のバージョンに戻せる
```

**パターン2: 見出し直前に予告文**
```markdown
次は、Gitのメリットについて見ていきましょう。

## Gitのメリット
```

### ✅ 推奨パターン

**パターン1: 説明文→箇条書き**
```markdown
## Gitのメリット

Gitを使うことで、以下のようなメリットがあります：

- 変更履歴を追跡できる
- 複数人での開発がしやすい
- 過去のバージョンに戻せる

これらのメリットにより、開発効率が大幅に向上します。
```

**パターン2: 見出し直後から本文**
```markdown
## Gitのメリット

Gitは、開発効率を大幅に向上させてくれる便利なツールです。変更履歴を自動で記録してくれるため、いつでも過去の状態に戻ることができます。

また、複数人での開発もしやすくなります。それぞれが独立して作業しながら、最後に統合することができるのです。
```

## 接続詞の活用（★v1.2.0で緩和★）

### 基本原則

- 文と文の自然な繋がりを作る
- **接続詞は「必要な箇所に適切に使う」。数を増やすこと自体が目的ではない**
- 文脈から繋がりが明確な場合は、接続詞なしでもOK

### 重要な考え方

- 無理に接続詞を入れて機械的な文章になるより、自然な流れを優先
- 同じ接続詞の連続使用（「また〜また〜」「そのため〜そのため〜」）は避ける
- **5文以上連続で接続詞なし**の場合のみ、繋がりを確認する

### 接続詞の種類と使い方

#### 順序関係
- 「まず」「次に」「最後に」
- 「はじめに」「続いて」

#### 原因・結果
- 「そのため」「だから」「その結果」
- 「このように」

#### 追加・拡張
- 「また」「さらに」「加えて」
- 「ちなみに」

#### 対比
- 「ですが」「一方」「しかし」
- 「とはいえ」

### 評価基準（v1.2.0更新）

**優（18-20点）**:
- 文と文の繋がりが自然でリズムがある
- 適切な接続詞で論理的な流れを作っている（使用率15-30%）
- 接続詞の重複がない

**良（14-17点）**:
- おおむね文の繋がりは良いが、やや単調
- 使用率が10-35%の範囲内

**可（10-13点）**:
- 接続詞の使いすぎ（35%超）でくどい
- または同じ接続詞の連続使用がある

**不可（0-9点）**:
- 5文以上連続で接続詞なしが複数箇所
- 接続詞が40%超で機械的な印象

## コード例の扱い

### 基本ルール

1. **コード例の前に必ず説明文を配置**
2. **コード内にコメントで補足説明**
3. **コード例の後に解説を追加**

### ✅ 推奨パターン

```markdown
以下のコマンドを順番に実行します：

\`\`\`bash
# すべての変更をステージングエリアに追加
git add .

# 変更を記録（コミット）
git commit -m "update"

# リモートリポジトリに送信
git push origin main
\`\`\`

1つずつ見ていきましょう。まず`git add .`で、現在のディレクトリ内のすべての変更をステージングエリアに追加します。
```

### ❌ 避けるべきパターン

```markdown
\`\`\`bash
git add .
git commit -m "update"
git push origin main
\`\`\`
```
→ 説明なしのコード例は避ける

## 箇条書きの使い方

### 基本ルール

1. **見出しの直後に箇条書きは配置しない**
2. **箇条書きの前に必ず導入文を配置**
3. **箇条書きの項目数は3-7個程度**

### ✅ 推奨パターン

```markdown
## ブランチのメリット

ブランチを使うことで、以下のようなメリットがあります：

- 新機能の開発中にバグ修正ができる
- 実験的な変更を安全に試せる
- 複数人で並行して開発できる
```

### ❌ 避けるべきパターン

```markdown
## ブランチのメリット

- 新機能の開発中にバグ修正ができる
- 実験的な変更を安全に試せる
- 複数人で並行して開発できる
```
→ 見出し直後の箇条書きは避ける

## 記事構成の基本パターン

### 技術記事（Qiita/Zenn）

```markdown
# タイトル

こんにちは、とまだです。

【読者への共感的な問いかけ】

【記事で得られる価値の明示】

## 忙しい人のために要約
- 要点1
- 要点2
- 要点3

## 〇〇とは（概念）
## 準備・環境構築（準備）
## 基本的な使い方（基礎）
## 実践：〇〇を作ってみる（応用）
## よくあるエラーと対処法（補足）
## まとめ（総括）
```

### 書籍・チャプター（Zenn Book）

```markdown
# チャプタータイトル

## 学習の目標

本章では、以下の内容を学習します。

- 〇〇を理解する
- △△を習得する
- □□を学ぶ

## はじめに

【トピックの概要と重要性】
【本章の位置づけ】

## メインコンテンツ
（5-8個のメイン見出し）

## まとめ

【本章で学んだことの振り返り】
【次章への導入】
```

## コンテンツ別の調整

### 技術記事（Qiita/Zenn）
- メイン見出し: 4-7個
- 詳細な説明重視
- 実践例を豊富に

### Zenn Book（教科書）
- メイン見出し: 5-8個（学習の目標・まとめ含む）
- 段階的理解を最優先
- 教育的な構成

### X投稿（Twitter）
- 一文の長さ: 全体で140-400文字
- 簡潔性を最優先
- 具体的な数値・ツール名を必ず含める
