# とまだ式評価ルール

**Version**: 3.4.0
**Last Updated**: 2025-01-22

このドキュメントは、とまだ式記事のLLM判断による評価ルールを統合したものです。
スクリプトで機械的にチェックできない、主観的な評価項目を定義しています。

> **Note**: v2.0.0 より、文体スタイル要素を統合。両面提示、読者の疑問先回り、括弧の活用を新評価項目として追加。

> **v3.0.0更新**: NG表現0件必須、各軸80%最低基準、逃げ道禁止ルールを追加。

> **v3.1.0更新**: 接続詞ルールを大幅緩和。「数を増やす」より「自然な流れ」を重視。推奨使用率を20-35%→15-30%に変更、3文連続→5文連続に緩和。

> **v3.2.0更新**: 共感的問いかけ・疑問先読みを必須からオプションに変更。無理に入れると文章が回りくどくなるため、自然な場合のみ使用。

> **v3.3.0更新**: 冒頭の共感的問いかけを評価対象から完全削除。デフォルトは「なし」に変更。冒頭は4要素（挨拶・結論先出し・価値提示・要約）のみで評価。

> **v3.4.0更新**: 「説明深度」軸を新設（15点）。概念の唐突な登場、説明が必要な一文の放置、補足・具体例の不足、Why/Howの欠如を評価。合計115点満点に変更。

## 合格条件（★全て満たすこと★）

1. **総合スコア109点以上**（115点満点の95%）
2. **各軸が最低基準（80%）を超えていること**
3. **NG表現が0件であること**（1件でも即不合格）

| 軸 | 配点 | 最低基準 |
|----|------|---------|
| 接続詞 | 20点 | 16点（80%） |
| NGワード | 15点 | **15点（100%）** |
| 文体品質 | 15点 | 12点（80%） |
| 文体スタイル | 15点 | 12点（80%） |
| 共感・トーン | 15点 | 12点（80%） |
| 説明深度 | 15点 | 12点（80%） |
| 冒頭構成 | 10点 | 8点（80%） |
| 導入フレーズ | 10点 | 8点（80%） |

### 禁止事項（逃げ道禁止ルール）

- **「スコアは低いが品質は高い」という判断は禁止**
- 最低基準未達の軸がある場合、改善せずに完了としてはならない
- NG表現が1件でもあれば、即座に改善を実行すること

## 1. 文体・トーン評価

### 1.1 親しみやすさ

**評価観点**:
- 適度なカジュアルさと丁寧さのバランスが取れているか
- 上から目線や教師的な口調になっていないか
- 「〜ですよね」「〜だと思います」など、対等な目線の表現があるか
- 専門用語を使う際に、分かりやすい説明が添えられているか

**避けるべき表現**:
- 「すべき」「当然」「必ず」（上から目線）
- 「素人は〜」「常識ですが」（見下し）

**推奨表現**:
- 「〜ですよね」「〜だと思います」「〜かもしれません」

### 1.2 共感表現

**評価観点**:
- 読者の悩みや不安に寄り添う表現があるか
- 「〜で困っていませんか？」「〜って難しいですよね」など、共感を示す問いかけがあるか
- 「私も最初は〜でした」など、著者自身の経験を共有しているか
- 記事の冒頭や各セクションで共感的な導入があるか

**推奨配置**:
- 各セクションの導入で共感表現
- 記事全体を通じて適度に配置

### 1.3 励まし・後押し（文体ルール更新）

**効果的な使い方**:
- 「一緒に〜していきましょう」- 伴走感を出す
- 「まずは〜から始めてみましょう」- ハードルを下げる
- **事実ベースの説明で自然に安心感を与える** ← とまだ式の特徴

**避けるべき表現**:
- **「大丈夫です」「安心してください」**: **原則使用禁止** ← とまだ式では事実ベースに置き換え
- 「実は」の多用（記事全体で1-2回まで）
- 「でも大丈夫です。実は〜」の組み合わせ（完全NG）
- 「思ったより簡単」「意外と簡単」「驚くほど簡単」
- 「〇分で完了」「数分で終わる」「すぐに完了」（時間の断言）

**とまだ式の代替アプローチ**:
```markdown
❌ 「大丈夫です、このコマンドは簡単です」
✅ 「このコマンドは3つのステップで実行できます」

❌ 「安心してください、失敗しても問題ありません」
✅ 「失敗しても git reset で元に戻せるので、気軽に試してみましょう」
```

### 1.4 両面提示（とまだ式の特徴）

**評価観点**:
- メリットだけでなくデメリットも正直に伝えているか
- 「一方で」「ただ」「とはいえ」を使って両面を示しているか
- 「神プロンプト」的な煽りへの距離感があるか
- 限界や注意点を正直に開示しているか

**推奨パターン**:
- 「〇〇は便利ですが、一方で△△には向かない場合もあります」
- 「ただ、〜という限界もあります」
- 「とはいえ、〜というリスクも存在します」

**チェックポイント**:
- [ ] 記事内で最低1箇所は両面提示があるか
- [ ] メリットを述べた後に限界や注意点を示しているか

### 1.5 読者の疑問を先回り（とまだ式の特徴）

**オプション**: この要素は必須ではありません。自然な流れで使える場合にのみ使用します。

**評価観点**（使用する場合）:
- 読者が「〜では？」と思いそうな疑問を先に拾っているか
- 疑問を拾った後に、適切な答えを示しているか

**パターン例**（使用は任意）:
- 「『〇〇では？』と思った方もいるかもしれません」
- 「ここまで聞いて『△△と何が違うの？』と思った方もいるかもしれません」
- 「『え、これ全部やらなきゃいけないの…？』と怯まれた方、ご安心ください」

**注意**: 無理に入れると文章が回りくどくなる場合があります。自然に読める場合のみ使用してください。

**チェックポイント**（使用する場合のみ）:
- [ ] 先回りした疑問に対して、具体的な回答を示しているか

### 1.6 括弧による補足・本音（とまだ式の特徴）

**評価観点**:
- 補足説明や本音を括弧で適度に挿入しているか
- 使いすぎていないか（1記事で2-4個程度）

**推奨パターン**:
- 「（これは揶揄する意図ではなく、事実としてそういうものも存在するという話です）」
- 「（正直私もまだ模索中ですが）」
- 「（ちなみにこの用途では〇〇が推しです）」

**チェックポイント**:
- [ ] 括弧を適度に活用しているか（1記事で2-4個程度）
- [ ] 括弧の内容が補足・本音として機能しているか

## 2. 構造・見出し評価

### 2.1 冒頭構成（文体ルール更新）

**必須要素（4つ）**:
1. **挨拶**: 「こんにちは、とまだです」で始まる
2. **結論先出し**: 今回伝えたいことの要点 ← とまだ式の特徴（重要）
3. **価値提示**: この記事で得られること
4. **要約セクション**: 「忙しい人のために要約」または類似のセクション

**とまだ式の全体構造**: 導入 → 結論先出し → 詳細解説 → 余談 → 締め

**冒頭パターンの例**:
```markdown
こんにちは、とまだです。

今回伝えたいことの要点は〇〇です。一言で言えば、△△ということになります。

この記事では、〇〇について解説します。読み終わる頃には△△ができるようになります。

## 忙しい人のために要約

- ポイント1
- ポイント2
- ポイント3
```

**チェックポイント**:
- [ ] 挨拶の後に結論先出し or 価値提示があるか

### 2.2 見出し構造

**メイン見出し（##）**:
- **個数**: 4-7個が理想
- **文字数**: 各見出しは30文字以内
- **階層**: 論理的な流れ（導入→本題→応用→まとめ）

**サブ見出し（###）**:
- メイン見出し1つにつき、2-5個

**H4見出し（####）**:
- 効果的に使用（補足情報、具体例、詳細説明）
- 内容は150文字以上、3段落以上で充実させる

**見出し直後のルール**:
- **必須**: 見出しの直後に1-2文の説明文を配置
- **NG**: 見出しの直後にいきなり箇条書き
- **NG**: 見出しの直後にいきなり別の見出し

**見出し前のルール**:
- **NG**: 「次は〜について説明します」といった前置き説明
- **推奨**: セクションの最後の文章で自然に次のトピックに繋ぐ、または直接次の見出しに入る

### 2.3 箇条書きの使い方

**ルール**:
1. **導入文が必須**: 箇条書きの前に、その内容を説明する1-2文を配置
2. **導入文は句点で終わる**: コロン（:）や全角コロン（：）で終わらせない
   - ❌ 「主なポイントは以下の通りです：」
   - ✅ 「主なポイントは以下の通りです。」
3. **締めの文が推奨**: 箇条書きの後に、まとめや次への接続を示す文を配置
4. **体言止め**: 各項目は体言止めで記述
5. **最大5個以内**: 6個以上は読みにくい

### 2.4 感情曲線の設計

記事全体で読者の感情が以下のように変化するよう設計:

1. **共感**（冒頭）: 「私も同じ悩みを持っていた」
2. **期待**（導入）: 「この方法で解決できそう！」
3. **納得**（本題前半）: 「なるほど、そういう仕組みか」
4. **挑戦**（本題後半）: 「自分でもやってみよう」
5. **安心**（応用・補足）: 「困った時の対処法も分かった」
6. **達成感**（まとめ）: 「できた！次のステップも見えてきた」

## 3. 抑揚・リズム評価

### 3.1 文末表現のバリエーション

| 文末パターン | 目安 | 例 |
|------------|---------|-----|
| **基本形** | 50-70% | 〜です、〜ます、〜でした、〜ました |
| **強調形** | 5-20% | 〜なのです、〜わけです、〜のです |
| **問いかけ形** | 3-15% | 〜でしょうか、〜ませんか |
| **理由形** | 5-20% | 〜から、〜ため、〜ので |

> **Note**: 共感形（〜ですね、〜ますね、〜ですよね）は評価対象外。自然な文章で無理に使う必要はない。

**NGパターン**:
- 同じ文末の3連続以上: 単調で読みにくい
- 基本形が80%超: 平坦で退屈
- 問いかけ形が20%超: 落ち着かない

### 3.2 接続詞の使用（★v3.1.0で大幅緩和★）

**基本方針**: 接続詞は「必要な箇所に適切に使う」。**数を増やすこと自体が目的ではない**。

**推奨使用率**: 15-30%（v3.0.0の20-35%から緩和）

**効果的な接続詞**:
| 関係 | 接続詞 |
|------|--------|
| 順接 | そのため、したがって、だから |
| 逆接 | しかし、ただし、一方で |
| 並列 | また、さらに、同様に |
| 例示 | 例えば、具体的には |
| 理由 | なぜなら、というのも |
| 言い換え | つまり、要するに |

**避けるべき接続詞**:
- 「それでは」→「では」または削除
- 「ですので」→「そのため」
- 「なので」→「そのため」「だから」

**自然さを重視したルール**:
- **接続詞なしで繋がりが明確な場合は、無理に追加しない**
- 同じ接続詞の2連続使用は避ける（「また〜また〜」等）
- 接続詞が30%を超えると文章がくどくなる傾向

**許容パターン（減点なし）**:
- 3-4文連続で接続詞なし: 文脈から繋がりが明確なら問題なし
- 使用率15%未満: 短い記事や箇条書き中心の場合は許容

**要改善パターン**:
- 5文以上連続で接続詞なし: 繋がりが不明瞭になりやすい
- 接続詞が35%超: 冗長で機械的な印象
- 同じ接続詞の連続使用: 「そのため〜そのため〜」等

### 3.3 問いかけと答えの構造

**効果的な問いかけ構造**:
1. **冒頭で大きな問いかけ**: 記事全体のテーマ
2. **各セクションで小さな問いかけ**: セクションの導入
3. **問いかけの後に必ず答えを示す**: 読者を放置しない

**問いかけのパターン**:
- **共感的問いかけ**: 「〜で困っていませんか？」
- **興味喚起の問いかけ**: 「なぜ〜なのでしょうか？」
- **選択を促す問いかけ**: 「AとB、どちらが良いでしょうか？」

**重要なルール**:
- 問いかけの後、2-3段落以内に答えを示す
- 答えのない問いかけは使わない
- 問いかけが多すぎない（文末表現の5-10%）

## 4. 表現・言い回し評価

### 4.1 日常的な例え

**効果的な例えの条件**:
- 身近な概念で説明（日常生活で体験していること）
- シンプル（例え自体が複雑にならない）
- くどくない（2-3文で完結）
- 適切なタイミング（複雑な概念を導入する直後）

**良い例え**:
```markdown
APIは、レストランのメニューのようなものです。お客さん（クライアント）は
メニュー（API仕様）を見て注文（リクエスト）し、キッチン（サーバー）が
料理（レスポンス）を提供します。
```

**避けるべき例え**:
- 別の技術用語で説明
- 複雑すぎる例え（5文以上かかる）
- 古すぎる例え
- 特定の文化・世代にしか通じない例え

### 4.2 導入フレーズ

| フレーズ | 使用タイミング |
|---------|--------------|
| 簡単に言うと | 複雑な概念の要約 |
| 例えば | 具体例を示す |
| 具体的には | 抽象的な説明の後 |
| つまり | 言い換え・要約 |
| 言い換えると | 別の表現で説明 |
| 要するに | 長い説明の後のまとめ |

**推奨使用頻度**:
- 記事全体で5-10回
- 各セクション（##見出し）に少なくとも1回

### 4.3 敬語レベル

**とまだ式の敬語バランス**:
- 基本は「です・ます調」
- 適度な口語表現（「〜ですよね」「〜かもしれません」）
- 初心者に対して失礼でない
- 親しみやすさを保つ

**避けるべき表現**:
- **過度に丁寧**: 「〜でございます」「〜いただけますでしょうか」
- **命令形**: 「〜しろ」「〜すべき」「〜しなければならない」
- **断定的**: 「〜に決まっている」「当然〜だ」
- **幼稚すぎる**: 「〜だよ」「〜だね」「〜しちゃおう」

### 4.4 具体性と抽象性のバランス

**効果的な説明パターン**:
1. **抽象的な説明（概念）**: まず全体像を示す
2. **具体的な例（実装）**: 次に実際のコードや手順を示す
3. **抽象への回帰（まとめ）**: 最後に再度概念に立ち戻る

**NGパターン**:
- 抽象的すぎる: 具体例がない
- 具体的すぎる: コードだけで説明がない
- 行ったり来たり: 抽象→具体→抽象→具体と混乱

### 4.5 読者への配慮表現

| パターン | 目的 | 例 |
|---------|------|-----|
| 励まし（事実ベース） | 不安を和らげる | 「〜という仕組みです」「手順はシンプルです」 |
| 共感 | 読者の気持ちを理解 | 「難しいですよね」「最初は混乱しますよね」 |
| 親しみ | 距離を縮める | 「一緒に見ていきましょう」 |
| 前提の確認 | 読者のレベルに配慮 | 「〇〇をご存じない方のために」 |
| 選択肢の提示 | 押しつけない | 「〜する方法もあります」 |

**推奨配置**:
- 冒頭: 共感＋励まし
- 中盤: 親しみ＋前提の確認
- 後半: 励まし＋選択肢の提示

**避けるべき表現**:
- 読者を決めつける: 「あなたは〜でしょう」
- 否定的: 「〜できないと困ります」
- 突き放す: 「調べてください」（補足なしで）

## 5. 説明深度評価（v3.4.0新設）

記事の「説明の深さ」「補足の充実度」を評価する。
スクリプトでは検出困難な、LLM判断による主観的評価軸。

### 5.1 概念の適切な導入（4点）

**評価観点**:
- 専門用語が初出時に説明されているか
- 略語が展開なしに使用されていないか
- 新しい概念に「〇〇とは」の説明があるか

**減点パターン**（-1点/件、最大-4点）:
- 「MCPサーバーを使用すると〜」← MCPの説明がない
- 「サブエージェントが〜」← サブエージェントとは何かの説明がない
- 「TDDで開発する」← TDDの略語展開がない

**改善例**:
```markdown
# Before
MCPサーバーを使用すると、外部ツールとの連携が可能になります。

# After
MCPサーバー（Model Context Protocol Server）を使用すると、外部ツールとの連携が可能になります。
MCPは、Claudeが外部のツールやデータソースと通信するための標準プロトコルです。
```

### 5.2 一文の完結性（3点）

**評価観点**:
- 「これは〇〇です」だけで終わり、読者が「だから何？」となる文がないか
- 因果関係が示されていない断定がないか
- 抽象的すぎて具体的にイメージできない文がないか

**減点パターン**（-1点/件、最大-3点）:
- 「フックは決定論的です」← だから何？
- 「これが重要です」← なぜ重要？
- 「コンテキストが管理できます」← どう管理できる？

**改善例**:
```markdown
# Before
フックは決定論的、CLAUDE.mdは助言的です。

# After
フックは決定論的、CLAUDE.mdは助言的です。
つまり、フックに設定した処理は例外なく毎回実行されますが、CLAUDE.mdの内容はClaudeが状況に応じて参考にするかどうかを判断します。
この違いを理解しておくと、どちらに何を書くべきか迷わなくなります。
```

### 5.3 補足・具体例の充実（4点）

**評価観点**:
- 箇条書きの直前に導入文があるか
- 表の直後に解釈や補足があるか
- コード例に説明があるか

**減点パターン**（-1点/件、最大-4点）:
- 見出し直後にいきなり箇条書き
- 表を示しただけで「この表から何がわかるか」の説明がない
- コードブロックの前後に「何をしているか」の説明がない

**改善例**:
```markdown
# Before
## MCPサーバーに接続する

- Notionからタスクを取得
- Figmaからデザインを参照
- データベースにクエリを実行

# After
## MCPサーバーに接続する

MCPサーバーを使うと、Claude Codeの能力を大幅に拡張できます。
たとえば、以下のような外部サービスとの連携が可能になります。

- Notionからタスクを取得
- Figmaからデザインを参照
- データベースにクエリを実行

これにより、コーディング作業中にブラウザを開かなくても、必要な情報にアクセスできます。
```

### 5.4 Why/Howの明示（4点）

**評価観点**:
- 「〇〇できます」だけでなく「なぜ有用か」が説明されているか
- 機能の列挙だけでなく「どう使い分けるか」が説明されているか
- 「重要です」と言いながら理由が示されているか

**減点パターン**（-1点/件、最大-4点）:
- 「サブエージェントを使えます」← なぜ使うと良いの？
- 「3つの方法があります」← どう使い分ける？
- 「これは重要なポイントです」← なぜ重要？

**改善例**:
```markdown
# Before
サブエージェントを調査に使用することをおすすめします。

# After
サブエージェントを調査に使用することをおすすめします。
なぜなら、調査で読み込んだ大量のファイル内容がメインの会話に蓄積されないからです。
メインのコンテキストを消費せずに深い調査ができるのは、長時間の開発セッションで大きなメリットになります。
```

### 5.5 チェックポイント

- [ ] 記事内のすべての専門用語に説明があるか
- [ ] 「だから何？」と思われる文がないか
- [ ] 箇条書き・表の前後に導入文・まとめ文があるか
- [ ] 機能紹介に「なぜ」「どう使う」が含まれているか

## 6. 太字強調評価

### 5.1 太字化の対象選定

**太字にすべきもの**:
1. 記事の核心となる主張
2. キーコンセプト（初出時のみ）
3. 行動のポイント（読者が実行すべきこと）
4. 対比・比較の要点
5. まとめや結論の重要部分

**太字にしてはいけないもの**:
1. 技術用語の羅列
2. 接続詞のみ
3. 文全体
4. 行全体
5. コロンで終わる文
6. コードブロック内
7. 見出しの一部

### 5.2 太字の割合

**推奨割合**: 5-15%（目標: 10%）

| 割合 | 評価 |
|------|------|
| 15%超 | 太字が多すぎて強調の効果が薄れる |
| 10-15% | 適切（理想的） |
| 5-10% | やや少ないが許容範囲 |
| 5%未満 | 太字が少なすぎて重要ポイントが埋もれる |

### 5.3 視覚的バランス

**セクションごとの分布**:
- 各セクションに太字が均等に分布
- 特定のセクションに集中していない

**段落ごとの分布**:
- 1つの段落に太字が2-3箇所以内
- 太字が連続していない

### 5.4 Markdown構文ルール

**リンク内の強調構文**:
- ✅ `**[リンクテキスト](URL)**`
- ❌ `[**リンクテキスト**](URL)`

**引用符内の強調構文**:
- ✅ `「**重要ポイント**」`
- ❌ `**「重要ポイント」**`

**強調構文の前後のスペース**:
- ✅ `**重要ポイント**について`
- ❌ ` **重要ポイント** について`

## 評価の実施方法

### スクリプトとの併用

機械的にチェックできる項目は `scripts/` 内のスクリプトで評価:
- `check_ng_words.py`: NGワード検出
- `check_structure.py`: 接続詞使用率、構造問題
- `check_sentence_endings.py`: 文末表現のバリエーション
- `calculate_score.py`: 総合スコア算出（v9.0.0で各軸最低基準チェック追加）

### LLM判断による評価

このドキュメントの評価ルールは、スクリプトでは判断できない主観的な品質を評価するためのものです。

**評価の流れ**:
1. スクリプトで機械的チェック → 定量スコア取得
2. 本ドキュメントに従い定性評価 → A+/A/B/C判定
3. 両方の結果を統合して改善提案

### 再実行判定（v3.0.0追加）

スクリプト出力の `requires_retry` フラグを確認:
- `requires_retry: true` → 最低基準未達の軸があるため再実行必須
- `failed_axes` 配列 → 基準未達の軸と不足点を確認

**再実行が必要な場合**:
1. `failed_axes` の各軸について改善を実施
2. 改善後、再度スクリプトを実行
3. 全軸合格まで繰り返し（最大5回）
