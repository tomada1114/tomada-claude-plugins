# コード例評価基準

この基準では、コード例の示し方と説明の質を評価します。

## 評価項目

### 1. コードの前後説明（30点）

**優（27-30点）**
- コードの前に必ず事前説明（1-2行）がある
- コードの後に重要ポイントの解説（2-3行）がある
- 何のコードか、なぜ必要かが明確

**良（21-26点）**
- 前後の説明はあるが、やや不十分
- 説明がやや形式的

**可（15-20点）**
- 前後の説明が一部欠けている
- 説明が不十分で理解しづらい

**不可（0-14点）**
- 前後の説明がほとんどない
- コードだけが羅列されている

### 2. コメントの適切性（25点）

**優（23-25点）**
- コード内に適切なコメントがある
- コメントで各部分の役割を説明している
- コメントが多すぎず、少なすぎない

**良（18-22点）**
- コメントはあるが、やや少ない
- もう少し詳しい説明があると良い

**可（13-17点）**
- コメントが少ない
- 重要な部分にコメントがない

**不可（0-12点）**
- コメントがほとんどない
- コードの理解が困難

### 3. コード例の段階性（25点）

**優（23-25点）**
- 基本的な例から始まっている
- 段階的に複雑な例に進んでいる
- 各段階で学ぶべきポイントが明確

**良（18-22点）**
- おおむね段階的だが、やや飛躍がある
- もう少し丁寧なステップがあると良い

**可（13-17点）**
- 段階性が弱い
- いきなり複雑な例が出てくる

**不可（0-12点）**
- 段階性が全くない
- コード例の選択が不適切

### 4. 良い例・悪い例の対比（20点）

**優（18-20点）**
- 良い例と悪い例が明確に示されている
- なぜ良い/悪いのかが説明されている
- 読者が違いを理解できる

**良（15-17点）**
- 対比はあるが、やや説明が不足
- もう少し違いを明確にすると良い

**可（10-14点）**
- 対比が弱い、または分かりにくい
- 違いの説明が不十分

**不可（0-9点）**
- 対比がない
- 良い例のみ、または悪い例のみ

## コード例の3点セット

すべてのコード例は以下の構造を持つべき：

```markdown
【事前説明】
以下のコードは〇〇を実現する基本的な例です。

【コードブロック】
```language
// コメントで各部分の役割を説明
const example = "サンプル";
```

【事後説明】
このコードのポイントは〇〇という部分です。
実際のプロジェクトでは〇〇も考慮する必要があります。
```

## コマンド例の特別ルール

bashコマンドやCLIコマンドを紹介する場合は、以下の形式を推奨します。

### 基本パターン

```markdown
### 基本的なコマンド

Gitの基本操作を理解するために、最もよく使うコマンドを紹介します。

```bash
# ファイルをステージングに追加
git add ファイル名

# ステージングした変更をコミット
git commit -m "コミットメッセージ"

# 変更の状態を確認
git status
```

これらのコマンドは、Gitを使う上で最も基本的なものです。
まずはこの3つを覚えることから始めましょう。
```

### コマンド例の必須要素

1. **導入文**: コマンドの目的を説明
2. **コメント付きコマンド**: 各コマンドに `#` でコメントを追加
3. **締めくくり**: 次のアクションを促す文章

### 締めくくりの例

- ✅ 「これだけ覚えておけば、基本的な操作はできます」
- ✅ 「まずはこの3つを覚えることから始めましょう」
- ✅ 「次の段階では〇〇について学んでいきます」

## 推奨されるコード説明パターン

### 事前説明の例
- 「以下のコードは〇〇を実現する基本的な例です」
- 「まず、最もシンプルな例から見ていきましょう」
- 「次に、〇〇を追加した例を見てみます」

### 事後説明の例
- 「このコードのポイントは〇〇です」
- 「実際のプロジェクトでは〇〇も考慮する必要があります」
- 「〇〇という点に注意してください」

## 避けるべきコード提示方法

- ❌ 説明なしでコードだけを提示
- ❌ コメントのないコード
- ❌ いきなり複雑なコードを提示
- ❌ エラー例やトラブルシューティングのみに偏る
- ❌ コード例が記事の大部分を占める

## 評価の進め方

1. すべてのコード例を確認する
2. 各コード例に前後の説明があるかチェックする
3. コメントの質と量を確認する
4. コード例の難易度の変化を確認する
5. 総合得点（100点満点）を算出する

## 改善のポイント

- コードの前には必ず「何のコードか」を説明
- コードの後には必ず「ポイント」を解説
- コード内の重要な行にはコメントを追加
- 複雑なコードは、より簡単な例を先に追加
- 良い例だけでなく、悪い例も示して違いを明確に
- コード例よりも文章での説明を重視する
