# 太字による重要ポイントの強調

## 目的

記事内の**重要な主張や覚えてほしいポイント**を太字で強調することで、読者の理解を助け、読みやすさを向上させます。

---

## ★重要★ CommonMark仕様の注意点

日本語Markdownで太字（`**`）を使う際、CommonMark仕様に起因する問題があります。**約物（括弧、カギ括弧など）が強調符号に直接接すると、太字が正しく表示されない場合があります。**

### 問題のあるパターン

以下のパターンは**太字にならない可能性があります**:

| パターン | 問題 | 表示結果（環境依存） |
|---------|------|-------------------|
| `**「重要」**` | 「」が`**`に接触 | **「重要」** ← 太字にならない可能性 |
| `**（補足）**` | （）が`**`に接触 | **（補足）** ← 太字にならない可能性 |
| `**『引用』**` | 『』が`**`に接触 | 太字にならない可能性 |
| `」**として` | 連続太字（閉じ括弧直後に次の太字開始） | レンダリングが崩れる可能性 |

### 解決策

#### 方法1: 約物を太字の外に出す（推奨）

```markdown
❌ 悪い例: **「これが重要」**です
✅ 良い例: 「**これが重要**」です

❌ 悪い例: **（補足情報）**を追加
✅ 良い例: （**補足情報**）を追加
```

#### 方法2: 約物を含まない部分だけ太字にする

```markdown
❌ 悪い例: **「Claude Codeを使うとAI駆動開発が加速する」**
✅ 良い例: 「**Claude Codeを使うとAI駆動開発が加速する**」
```

#### 方法3: 連続太字を分離する

閉じ括弧の直後に次の太字が始まるパターンは、助詞を太字の外に出すことで解決できます。

```markdown
❌ 悪い例: 「**ナビゲーション**」**として機能する構成**
✅ 良い例: 「**ナビゲーション**」として**機能する構成**

❌ 悪い例: 「**Update Policy**」**と明記**
✅ 良い例: 「**Update Policy**」と**明記**
```

#### 方法4: HTML直書き（最終手段）

どうしても約物を含めて太字にしたい場合:

```markdown
<strong>「重要なポイント」</strong>
```

検出されるパターン:

- `**（` / `）**` （丸括弧との接触）
- `**『` / `』**` （二重カギ括弧との接触）
- `**【` / `】**` （隅付き括弧との接触）

自動修正可能なパターン（`--fix` オプション）:
- `**「内容」**` → `「**内容**」`（括弧を外に移動）
- `」**として` → `」として**`（助詞を太字の外に移動）

### 太字化がもたらす効果

1. **視認性の向上**: 重要なポイントが一目で分かる
2. **記憶の定着**: 強調された部分が記憶に残りやすい
3. **スキャン読みの促進**: 流し読みでも要点を把握できる
4. **情報の階層化**: 重要度に応じた視覚的なメリハリ

## 太字化の基本方針

### 対象となる内容

- **記事の核心となる主張や結論**
- **読者が理解・記憶すべきキーコンセプト**
- **行動のポイント**（「〜することが大切」など）
- **対比や強調**（「〜ではなく〜」など）
- **注意点や重要な制約**

### 対象外の内容

- 技術用語の機械的な羅列（Git、React、TypeScriptなど単語のみ）
- 接続詞や助詞のみ（「しかし」「この」など）
- 冒頭の挨拶や要約セクション（既に構造で強調されている）
- 見出しや箇条書きの項目（既に構造で強調されている）

### 太字化の割合

- **推奨**: 全体の約10%
- **許容範囲**: 5-15%
- **過剰**: 15%を超える（読みづらくなる）
- **不足**: 5%未満（強調の効果が薄い）

## 太字化の基準

### 判断プロセス

1. **記事全体を読み直す**: 各セクションの主張を理解する
2. **重要ポイントを特定**: 読者が覚えるべき部分を見つける
3. **文の一部を選択**: 句や節レベルで選択（文全体ではない）
4. **太字化**: `**強調部分**` の形式で記述
5. **バランスを確認**: 割合と配置のバランスをチェック

### 何を太字にするか

#### ✅ 太字化すべき内容

**1. 重要な主張や結論**
```markdown
Gitでコミットを作成する際は、**変更内容を明確に記述すること**が大切です。
```

**2. キーコンセプト**
```markdown
React Hooksを使うことで、**関数コンポーネントでも状態管理**ができるようになりました。
```

**3. 行動のポイント**
```markdown
大切なのは、エラーを恐れずに**まず試してみる姿勢**です。
```

**4. 対比**
```markdown
重要なのは**完璧なコードを書くこと**ではなく、**動くコードを書いて改善すること**です。
```

**5. 注意点や制約**
```markdown
ただし、**公開リポジトリには機密情報を含めない**ように注意してください。
```

**6. 問題解決のポイント**
```markdown
このエラーを解決するには、**パスを絶対パスで指定する**必要があります。
```

#### ❌ 太字化すべきでない内容

**1. 技術用語の羅列**
```markdown
悪い例: **Git**、**React**、**TypeScript**を使います。
理由: 単語を並べただけで、文脈的な重要性がない
```

**2. 接続詞や助詞のみ**
```markdown
悪い例: **しかし**、ここで注意が必要です。
悪い例: この**の**説明をします。
理由: 文法的な要素のみで、意味のある強調にならない
```

**3. 文全体**
```markdown
悪い例: **Gitでコミットを作成する際は、変更内容を明確に記述することが大切です。**
理由: 文全体を太字にすると、どこが重要か分からなくなる
```

**4. 過剰な太字**
```markdown
悪い例: **Git**で**コミット**を作成する際は、**変更内容**を明確に記述することが**大切**です。
理由: 太字が多すぎて、かえって読みづらくなる
```

**5. 箇条書き項目全体**
```markdown
悪い例: **- 重要なポイント**
理由: 箇条書き自体が既に構造的な強調になっている
```

## NGパターンと対処法

### パターン1: 句点で終わる文全体の太字

**問題**:
```markdown
**Gitでコミットを作成する際は、変更内容を明確に記述することが大切です。**
```

**対処法**:
文の中で最も重要な部分（句や節）だけを太字にする

**修正例**:
```markdown
Gitでコミットを作成する際は、**変更内容を明確に記述すること**が大切です。
```

### パターン2: 接続詞のみの太字

**問題**:
```markdown
**しかし**、ここで注意が必要です。
```

**対処法**:
接続詞は太字にせず、その後の重要な内容を太字にする

**修正例**:
```markdown
しかし、ここで**エラーハンドリングを適切に行う**ことが必要です。
```

### パターン3: 技術用語の機械的な太字化

**問題**:
```markdown
**Git**、**GitHub**、**GitLab**の違いを理解しましょう。
```

**対処法**:
文脈における重要性を判断し、主張や結論を太字にする

**修正例**:
```markdown
Git、GitHub、GitLabの違いを理解することで、**適切なツールを選択**できます。
```

### パターン4: 過剰な太字化

**問題**:
```markdown
**Git**で**コミット**を作成する際は、**変更内容**を**明確に**記述することが**大切**です。
```

**対処法**:
1つの文で1〜2箇所のみ太字にする

**修正例**:
```markdown
Gitでコミットを作成する際は、**変更内容を明確に記述すること**が大切です。
```

## 実践的なヒント

### ヒント1: 「覚えてほしい」基準で判断する

読者に「これは覚えておいてほしい」と思う部分を太字にします。

**例**:
```markdown
コミットメッセージは、**他の開発者が理解できるように**書くことが重要です。
```

### ヒント2: 声に出して読む

太字にした部分を強調して読み上げ、自然に聞こえるか確認します。

**自然な例**:
```markdown
大切なのは、**完璧を目指さず、まず動かすこと**です。
（読み上げ: 大切なのは、【完璧を目指さず、まず動かすこと】です。）
```

**不自然な例**:
```markdown
**大切なのは、完璧を目指さず、まず動かすことです。**
（読み上げ: 【大切なのは、完璧を目指さず、まず動かすことです。】← 文全体を強調すると不自然）
```

### ヒント3: 1段落に1〜2箇所

1つの段落で太字にするのは1〜2箇所に抑えます。多すぎると視覚的にうるさくなります。

**適切な例**:
```markdown
Gitのブランチ機能を使うことで、**複数の機能を並行して開発**できます。この機能は、チーム開発において**作業の衝突を防ぐ**ために不可欠です。
```

### ヒント4: セクションごとにバランスを取る

各セクションに均等に太字を配置し、特定のセクションだけに集中しないようにします。

### ヒント5: 見出しや箇条書きと競合させない

見出しや箇条書きの項目自体は太字にしません。それらは既に構造的に強調されています。

**適切な例**:
```markdown
### コミットメッセージの書き方

コミットメッセージは、**変更の理由を明確に**書くことが大切です。

- 変更内容の要約
- 変更の理由
- 影響範囲

この3つの要素を含めることで、**他の開発者が理解しやすい**メッセージになります。
```

## よくある質問

### Q1: 技術用語は太字にすべきですか？

A: **文脈によります。** 技術用語が記事の核心で、初出の場合や特に強調したい場合は太字にしても良いですが、単に技術用語を並べるだけなら太字にする必要はありません。

**良い例**:
```markdown
今回は**useState**という重要なフックを学びます。
```

**不要な例**:
```markdown
**Git**でコミットします。（単に技術用語を使っているだけ）
```

### Q2: 複数の文を太字にしても良いですか？

A: **基本的には避けるべきです。** 複数の文にまたがる場合は、最も重要な部分（句や節）だけを選んで太字にします。

**避けるべき例**:
```markdown
**Gitは分散型バージョン管理システムです。変更履歴を管理できます。**
```

**推奨例**:
```markdown
Gitは分散型バージョン管理システムで、**変更履歴を効率的に管理**できます。
```

### Q3: 太字が5%未満でも問題ないですか？

A: **問題ありませんが、推奨はされません。** 適度な太字は読みやすさを向上させるため、重要なポイントがあれば積極的に太字化することをお勧めします。

### Q4: コードブロック内のコードは太字にできますか？

A: **Markdownの制約上、推奨しません。** コードブロック内では太字が適切に表示されない場合があります。代わりに、コードの前後の説明文で重要な部分を太字にします。

**推奨例**:
```markdown
以下のコードでは、**エラーハンドリングを適切に行う**ことが重要です。

\`\`\`javascript
try {
  // コード
} catch (error) {
  console.error(error);
}
\`\`\`
```

### Q5: 箇条書き内の一部を太字にできますか？

A: **はい、できます。** 箇条書き項目全体ではなく、項目内の重要な部分を太字にするのは効果的です。

**良い例**:
```markdown
- コミットメッセージには**変更の理由**を含める
- 1つのコミットには**1つの変更のみ**を含める
- **明確で簡潔な**メッセージを心がける
```

## チェックリスト

太字化を実施した後、以下をチェックします：

- [ ] 太字の割合が5-15%の範囲内か
- [ ] 句点で終わる文全体を太字にしていないか
- [ ] 接続詞や助詞のみを太字にしていないか
- [ ] 1段落に太字が3箇所以上ないか
- [ ] 技術用語を機械的に太字にしていないか
- [ ] 見出しや箇条書き項目全体を太字にしていないか
- [ ] 各セクションにバランスよく太字が配置されているか
- [ ] 声に出して読んで自然に聞こえるか

## まとめ

太字による強調は、**読者の理解を助ける**重要な手法です。ただし、**過度に使用すると逆効果**になるため、バランスが大切です。

**覚えておくべき3つのポイント**:
1. **文脈における重要性を判断**して太字化する
2. **文全体ではなく、句や節レベル**で太字にする
3. **全体の約10%を目安**に、適度に使用する

これらのガイドラインに従うことで、読みやすく、理解しやすい技術記事を作成できます。
